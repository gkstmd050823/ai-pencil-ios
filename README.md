# AI 펜슬 (아이패드)

PDF에 애플 펜슬로 필기하다가 모르는 부분에 동그라미를 치면 그 부분을 설명해 주는 앱의 아이패드판. 안드로이드판을 Swift, PencilKit, PDFKit으로 다시 만드는 중이다.

지금 들어 있는 것:

- 서재: PDF 가져오기, 종이를 골라 새 노트 만들기(백지·줄·모눈·점·코넬), 폴더, 정렬, 문서 찾기, 이름 바꾸기
- 필기: 만년필·펜·볼펜·연필(굵기는 밀리미터 단위로 0.1~2.0, 도구 막대에 굵기 세 칸; 필압 감도와 획 안정화; 색 18가지와 직접 고르기), 글자를 가리지 않는 형광펜, 지우개(획/부분, 둘 다 크기 조절, 형광펜만 지우기, AI 펜 표시 지우기, 이 쪽 필기 모두 지우기), 도형(직선·화살표·네모·동그라미), 올가미, 실행 취소, 한 번 쓰고 나면 이전 도구로 돌아가기(지우개·형광펜·도형), 애플 펜슬 두 번 탭과 꽉 쥐기
- 문서 탭(연 문서가 쪽 위에 탭으로 남고, 눌러서 오가고, ×로 닫는다), 읽기 전용 모드(눈 모양 단추: 손가락은 넘기기만, 펜은 AI 펜만), 쪽을 골라 PDF로 내보내기("1-3, 7"), 문서 합치기(서재에서 문서를 길게 눌러 "다른 문서와 합치기")
- 서재: 문서를 여러 개 또는 전부 골라 한꺼번에 옮기기·합치기·삭제(오른쪽 위 체크 단추), 문서를 끌어서 폴더에 넣기(폴더 안에서는 "폴더 밖으로" 칸에 놓기)
- 글자 고르기·복사·번역: 손가락 필기가 꺼져 있을 때(읽기 전용 포함) 글자 위를 손가락으로 잠깐 누르고 있으면 그 낱말이 골라지고, 그대로 끌면 손가락까지의 글이 골라진다. 손을 떼면 "복사 · 번역" 메뉴가 뜨고 양 끝의 손잡이로 범위를 고친다. "번역"은 쪽 아래 카드에 번역을 보여 준다(Claude Haiku 5.5). 카드의 "글자를 고르면 바로 번역"을 켜면 메뉴를 거치지 않는다. 글자가 파일에 들어 있는 PDF와 글자 인식(OCR)을 거친 스캔본에서 된다
- PDF 가져오기: PDF가 들어올 때마다(서재의 "PDF 가져오기", 문서 화면 ⋯ → "PDF 가져오기", 다른 앱에서 "AI 펜슬로 열기") 어디로 갈지 묻는다. "새 문서로"면 넣을 폴더를 고르고, "열린 문서에 추가"면 탭으로 열려 있는 문서 가운데 하나를 골라 그 문서의 쪽으로 넣는다(화면에 떠 있는 문서는 읽던 쪽 뒤나 맨 끝, 다른 탭의 문서는 맨 끝). 뒤쪽의 필기·수식·AI 표시·책갈피는 제 쪽을 따라 밀린다
- 문서: 쪽 이동, 목차, 책갈피, 문서 안 검색, 세로로 이어 보기/가로로 한 쪽씩/두 쪽씩 세로로/두 쪽씩 가로로 넘기기, 종이 골라 쪽 추가, 어두운 종이, 필기 포함 PDF 내보내기, LaTeX 수식
- AI 펜: 동그라미 친 부분을 Claude가 설명(필요하면 웹 검색), 이어 묻기, 설명 창 크기 조절, 질문 목록(문서 화면 위의 말풍선 단추, AI 펜을 들었을 때 도구 막대의 단추, 설명 창의 목록 단추)

iPadOS 17.5 이상에서 돈다.

## AI 펜

도구 막대의 반짝이 모양이 AI 펜이다. 모르는 부분에 동그라미를 치거나 밑줄을 그으면 그 쪽 전체 그림과 표시한 부분의 확대 그림, 문서 본문 텍스트가 Claude에게 가고, 설명이 옆(가로 화면)이나 아래(세로 화면) 창에 글자가 오는 대로 나온다. 창 아래에서 이어서 물을 수 있다.

- 처음 한 번, 설정(서재 왼쪽 위 톱니바퀴 또는 문서 화면의 ⋯ → 설정)에 본인의 Claude API 키를 넣어야 한다. 키는 <https://console.anthropic.com> 의 API Keys에서 만든다. 사용한 만큼 요금이 나온다.
- 키는 아이패드의 키체인에만 저장되고 api.anthropic.com으로 보내는 요청에만 쓰인다. 키체인이 받아 주지 않는 드문 경우에는 앱 내부 저장소의 파일(파일 앱에서 보이지 않고 백업에서 빠지는 곳)에 둔다.
- 기본 모델은 Opus 5.5다. 가장 정확하지만 질문당 비용도 가장 높다. 설정에서 Sonnet 5.5나 Haiku 5.5로 바꿀 수 있고, 설명 깊이·언어·문서를 얼마나 참고할지도 거기서 고른다.
- 표시는 쪽에 청록색으로 남고 옆에 작은 단추가 붙는다. 단추를 누르거나(손가락 필기가 꺼져 있으면 표시 안쪽을 손가락으로 눌러도 된다) AI 펜으로 표시를 톡 건드리면 저장된 설명이 다시 열린다. 이때는 Claude에게 다시 묻지 않는다.
- 웹 검색: 설정에서 켜 두면(기본값) 요청에 `web_search_20250305` 도구가 함께 간다. 검색할지는 Claude가 정하고, 검색한 답에는 근거가 된 쪽의 번호와 끝에 출처 목록이 붙는다. 한 답에 최대 3번, 검색 1,000회에 10달러가 토큰 요금과 따로 든다. 이어 물을 때는 검색 호출과 결과, 인용이 받은 그대로(봉인된 부분 포함) 되돌아간다. 조직에서 웹 검색을 꺼 둔 키면 검색 없이 답하고 그렇게 알린다.
- 표시를 치우는 방법: 설명 창의 ⋯ → "쪽의 표시만 지우기"(설명은 남는다) 또는 "이 표시와 설명 삭제", 단추를 길게 눌러 나오는 같은 메뉴, 문서 화면 ⋯ → "AI 표시 보이기"를 꺼서 전부 숨기기. 지우개로 표시를 문질러도 표시만 쪽에서 사라진다(실행 취소로 되돌아오고, 지우개 설정에서 끌 수 있다). 지운 표시의 설명은 질문 목록에 남아 있고, 목록에서 그 질문을 길게 누르거나 오른쪽으로 밀면 표시를 다시 보이게 할 수 있다.

## 맥 없이 빌드하기

개발 PC가 Windows라서 빌드는 GitHub Actions의 macOS 러너가 한다.

- `project.yml`: XcodeGen 설정. 빌드 서버가 여기서 Xcode 프로젝트를 만든다(프로젝트 파일은 저장소에 두지 않는다).
- `.github/workflows/build.yml`: `main`에 올릴 때마다 시뮬레이터용으로 빌드해 화면을 찍고, 아이패드용으로 빌드해 서명 없는 IPA를 만든다.
- 결과물은 Actions → 해당 실행 → Artifacts에 있다: `AIPencil-ipa`(설치 파일), `screenshots`(시뮬레이터 화면과 아래의 가짜 서버 기록), 실패하면 `logs`.
- `tools/mock_claude.py`: Claude API를 흉내 내는 가짜 서버. 빌드 서버가 이것을 띄우고 디버그 빌드를 `-apiBase http://127.0.0.1:8787`로 실행해, 키 없이 "표시 → 요청 → 글자가 흘러나옴 → 이어 묻기"를 끝까지 돌려 본다. 앱이 보낸 요청의 요약(`mock.log`)과 함께 간 그림(`mock-dump/`)이 결과물에 들어 있다. 릴리스 빌드(IPA)는 `-apiBase`를 무시한다.
- `tools/tricky.pdf`: 돌아간 쪽과 잘린 쪽이 있는 시험용 PDF. 그런 쪽에서도 Claude에게 가는 그림의 표시 위치가 화면과 같은지 본다.

## 아이패드에 설치하기

IPA에는 서명이 없어서 그대로는 설치되지 않는다. Windows의 Sideloadly가 본인 Apple ID로 서명해 넣어 준다.

1. Artifacts에서 `AIPencil-ipa`를 내려받아 압축을 풀면 `AIPencil.ipa`가 나온다.
2. PC에 Sideloadly와 iTunes(Apple 기기 드라이버)를 설치하고, 아이패드를 USB로 연결해 "이 컴퓨터를 신뢰"를 누른다.
3. Sideloadly에 `AIPencil.ipa`를 끌어다 놓고 Apple ID를 입력한 뒤 Start.
4. 아이패드에서 설정 → 일반 → VPN 및 기기 관리 → 본인 Apple ID → 신뢰.
5. 설정 → 개인정보 보호 및 보안 → 개발자 모드를 켜고 재시동한다(iPadOS 16 이상).

무료 Apple ID로 서명한 앱은 7일 뒤 만료된다. 같은 방법으로 다시 설치하면 되고, 앱 안의 문서와 필기는 남는다. Sideloadly의 자동 갱신을 켜 두면 PC와 같은 Wi-Fi에 있을 때 알아서 갱신한다.

필기는 PDFKit의 쪽 오버레이(iPadOS 16)에 쪽마다 PencilKit 캔버스를 하나씩 얹어 받는다. 캔버스의 좌표는 쪽 왼쪽 위에서 잰 쪽 좌표와 같다(빌드 서버에서 제목 둘레에 고리를 그려 확인했다). PDFKit은 오버레이를 늘려서 확대하므로 그대로 두면 필기의 픽셀도 같이 늘어나 선이 흐려진다. 그래서 캔버스를 확대 배율만큼 크게 만들어 자기 그림을 그만큼 확대해 그리게 한 뒤 쪽 크기로 줄여 놓는다. 좌표는 그대로이고 픽셀만 그만큼 많아진다. 쪽 전체를 덮는 캔버스는 쪽의 3배까지만 만든다(그보다 크면 메모리와 그리는 일이 너무 커진다). 0.7.0까지는 그래서 3배 넘게 확대하면 필기만 거칠어졌다: 화면 맞춤이 2.27배이고 5배까지 확대되는 아이패드에서 캔버스 타일은 점당 6픽셀, 쪽 타일은 10픽셀이었다(0.7.0의 진단 정보로 받은 수치). 0.7.1부터는 그 크기를 넘는 배율에서 캔버스가 쪽 전체가 아니라 보이는 부분과 그 둘레만 덮는다(`canvasWindow`). 캔버스는 스크롤 뷰이므로 그림은 여전히 쪽 전체이고 그 부분으로 스크롤해 둘 뿐이다. 캔버스가 차지하는 크기는 전과 같거나 작고, 세밀함은 PDFKit이 확대되는 데까지(5배) 화면 해상도를 따라간다. PDFKit의 스크롤 뷰를 지켜보다가 보이는 부분이 캔버스 밖으로 나가려 하면 캔버스를 옮기며, 펜이 닿아 있는 동안에는 옮기지 않는다. 3배 이하에서는 0.6.0과 똑같이 쪽 전체를 덮는다. 돌려서 보여 주는 쪽(/Rotate가 있는 쪽)에서는 PDFKit이 오버레이를 돌리기 전 쪽의 틀로 놓고 쪽과 함께 돌린다. 그래서 필기와 표시는 돌리기 전 좌표로 저장되고, Claude에게 보낼 그림을 만들 때만 화면에 보이는 방향으로 돌려 그린다. 펜, 형광펜, 지우개, 올가미는 쪽 위의 도구 막대에서 고른다.

수식은 상단의 Σ 버튼에서 LaTeX로 입력한다. KaTeX로 조판한 미리보기를 그림으로 떠서(글자 모양만 남기고 색은 그릴 때 입힌다) 쪽의 필기 아래에 놓는다. 도구 막대의 "수식 옮기기"를 고르면 필기 캔버스가 비켜서, 수식을 끌어 옮기거나 길게 눌러 수정·복제·삭제할 수 있다.

빈 쪽은 PDF 자체에 끼워 넣고, 그 뒤 쪽들의 필기 파일과 수식·질문의 쪽 번호를 한 쪽씩 뒤로 옮긴다.

AI 펜은 PencilKit의 펜으로 그리게 한 뒤, 획이 끝나면 그 획을 캔버스에서 도로 빼서 표시로 따로 보관한다(필기와 섞이지 않고, 지우개나 올가미에 걸리지 않는다). Claude에는 공식 Swift SDK가 없어 HTTPS로 직접 요청한다. 요청 형식은 안드로이드판과 같다: 지침과 문서 본문(1시간 캐시)을 system에, 쪽 그림 두 장과 질문을 messages에 넣고 스트리밍으로 받는다. 이어 물을 때는 앞선 답의 블록(생각 블록과 서명 포함)을 받은 그대로 되돌려 보낸다.

펜 종류는 만년필(누르는 힘에 따라 굵기가 변함), 펜(조금 변함), 볼펜(굵기 일정), 연필이다. 연필만 PencilKit의 잉크이고 나머지는 앱 자체 펜이다(아래). 굵기는 종이 위의 밀리미터로 정한다(0.8.0): 0.5는 쪽에서 0.5mm, 곧 1.42포인트다. 도구 막대에 굵기 세 칸이 있어 눌러서 바꾸고, 쓰고 있는 칸을 한 번 더 누르면 뜨는 창의 슬라이더가 그 칸의 굵기를 0.05mm씩 바꾼다. 0.7.1까지는 PencilKit의 굵기 값을 그대로 슬라이더에 올려서, 값 1이 선 2포인트였고 2.3 아래에서는 또 다른 기울기라 조금만 움직여도 굵기가 크게 달라졌다. 전에 저장된 굵기는 같은 굵기의 밀리미터 값으로 옮겨진다. 실행 취소는 창의 실행 취소 기록을 쓴다.

애플 펜슬 두 번 탭과 꽉 쥐기는 `UIPencilInteraction`으로 받는다. 무엇을 할지는 앱 설정에서 고르고, "아이패드 설정 따르기"로 두면 시스템의 펜슬 설정을 따른다.

돌려서 보여 주는 쪽에 넣은 수식은 쪽이 돌아간 만큼 반대로 돌려서 화면에서 똑바로 서게 한다.

도구 막대는 도구마다 내용이 다른 오른쪽 칸의 폭을 고정해서, 어떤 도구를 들어도 크기와 자리가 같다.

iOS 27과 선명도: 0.6.0까지 받은 "문서가 낮은 해상도로 보인다", "필기가 낮은 해상도로 보인다"는 보고는 iPadOS 27.2의 실기기에서 나왔고, 빌드 서버의 시뮬레이터(iOS 26)에서는 한 번도 나오지 않았다. iOS 27의 PDFKit에는 쪽 위의 일부 레이어를 1배 해상도로 그려 늘려 보여 주는 결함이 보고돼 있다(주석 레이어 `PDFPageLayerAnnotationEffect`의 `contentsScale`이 1.0, 애플 개발자 포럼 845260·847155, FB24882188). 이 앱에서 무엇이 그 영향을 받는지는 실기기의 수치로만 알 수 있어서, 설정의 진단 정보에 보고 있는 쪽의 레이어마다 크기와 해상도 배율을 적어 넣는다(`describeView`). 쪽 내용은 아래의 "한 번 더 그리기"로 실기기에서 선명해진 것을 확인받았다.

앱 자체 펜(0.7.0에서는 설정으로 켜는 것이었고, 0.8.0부터는 이것이 펜이다): PencilKit은 쓰는 동안의 선을 자기가 그리고, 손떨림을 펴거나 필압 반응의 세기를 바꾸는 값을 받지 않는다. 0.5.0에는 획이 끝난 뒤에 굵기를 고쳐 넣는 "필압" 슬라이더가 있었는데 손을 뗀 뒤에 선이 바뀌어 어색해서 0.6.0에서 뺐다. 펜(연필 제외), 형광펜, AI 펜의 터치는 앱이 직접 받는다(`PenGesture`). 터치마다 선이 펜 쪽으로 일정 비율씩 다가가게 해서 손떨림을 펴고(획 안정화, 가장 높을 때 선이 펜을 약 0.085초 늦게 따라온다), 누르는 힘으로 굵기를 정해(필압 감도) 화면 해상도의 채운 도형으로 바로 보여 준다. 펜을 떼면 그 선을 PencilKit 획(점마다 굵기가 적힌 "monoline" 잉크)으로 캔버스에 넣는다. 그래서 지우개, 올가미, 실행 취소, 내보내기는 전과 같이 통한다. "pen" 잉크는 굵기를 적어 줘도 선 끝을 가늘고 흐리게 만들어 손을 떼는 순간 모양이 바뀌어서 쓰지 않는다. PencilKit은 점에 적힌 크기대로 선을 그리지 않는다: monoline 잉크는 크기 2 이하에서는 아무것도 그리지 않고, 그 위로 1마다 2포인트씩 굵어진다(빌드 서버에서 크기 4·8·12의 직선이 4·12·20포인트로 그려졌다). 그래서 선은 눈에 보일 굵기로 계산하고, 넘길 때만 그 굵기가 나오는 PencilKit 크기로 바꾼다(`InkWidth`). 도형 도구도 같은 환산을 쓴다. 만년필은 필압 감도 그대로, 펜은 그 0.4배, 볼펜은 굵기가 일정하다. 연필만 PencilKit이 그린다. AI 펜의 선은 획이 되지 않고 바로 질문이 된다. 손가락으로 쓸 때는 손가락이 조금 움직이거나 0.15초 머문 뒤에 선으로 치고, 그 전에 둘째 손가락이 닿으면 스크롤·확대에 양보한다.

기본값이 끔인 까닭: 쓰는 동안의 선을 PencilKit은 지연을 줄이는 전용 경로로 그리고, 앱은 보통의 레이어로 그린다. 둘의 지연 차이는 실기기에서만 잴 수 있다. 펜이 손을 늦게 따라오게 되는 일은 없어야 하므로, 직접 켜서 비교해 보고 쓰도록 했다. 끄면 0.6.0과 같은 경로로 쓴다.

필기를 앱이 그리기(0.8.0, `InkPaint`): 펜을 떼면 선이 다시 무뎌진다는 보고의 원인은 캔버스 배율이었다. 캔버스를 확대 배율의 4분의 1 단위로 올림해서, 화면 맞춤 2.219배인 아이패드에서 캔버스는 2.25배로 그려진 뒤 70분의 1만큼 줄여져 화면 픽셀과 어긋났다(쓰는 동안의 선은 앱이 화면 픽셀에 맞춰 그리는 도형이라 선명했다). 0.8.0은 두 가지를 했다. 캔버스 배율을 확대 배율과 정확히 같게 했고, 다 쓴 필기도 앱이 직접 그린다: 쪽의 획을 메인 스레드 밖에서 화면 픽셀 그대로의 그림으로 그려 캔버스 대신 보여 준다. 굵기가 점마다 적힌 평범한 획(자체 펜, 도형, 형광펜이 만드는 획)은 쓰는 동안 보이던 것과 같은 도형으로 그리고, 그 밖의 획(연필, 부분 지우개가 자른 획, 예전 버전의 PencilKit 펜 획)은 PencilKit에게 그 자리만 그리게 해서 같은 그림에 넣는다. 선을 쓰면 그 선은 그림에 들어갈 때까지 쓰던 도형 그대로 떠 있고(손을 0.25초쯤 쉬면 그림에 들어간다), 그림은 바뀐 자리만 다시 그린다. 그래서 펜을 떼는 순간 보이는 것이 바뀌지 않는다. 캔버스는 그대로 밑에 있고 획도 그대로 PencilKit 획이다. 캔버스가 보이는 때는 캔버스에서 일하는 도구(올가미, 부분 지우개, 연필)를 들었을 때, 그림이 아직 없을 때, 확대한 채 스크롤해서 그림이 닿지 않는 곳이 보일 때다. 쪽 전체가 1,300만 화소 안에 들면 쪽 전체를 한 장으로 그리고(큰 아이패드의 화면 맞춤 배율이 950만 화소다), 넘으면 보이는 부분과 그 둘레만 그린다. 화면에서 먼 쪽의 그림은 버린다. 그림의 픽셀은 화면의 픽셀에 맞춘다: PDFKit은 쪽을 확대 배율이 정하는 대로 소수점 위치에 놓아서(빌드 서버의 화면 맞춤에서 첫 쪽이 0.6픽셀 어긋나 있었다) 쪽 모서리에서 시작하는 그림은 그만큼 밀려 보이며 선 가장자리가 반 픽셀씩 번졌다. 그래서 그림을 화면 픽셀이 시작하는 자리부터 그리고(`pixelGrid`), 쪽 그림(`PagePicture`)도 같은 자리에 맞췄다. 0.7.0의 "필기 그림"은 쓰는 동안 캔버스로 돌아가서 펜을 댈 때마다 필기가 바뀌어 보였고, 그래서 0.7.1에서 뺐던 것이다. 이번에는 쓰는 동안에도 그림과 도형이 보이고 캔버스로 돌아가지 않는다.

형광펜(0.8.0): PencilKit의 형광펜은 색을 덧칠해서 한 번만 그어도 글자가 흐려지고 겹치면 가려졌다. 이제 형광펜 획은 반투명한 색의 평범한 획으로 저장하고, 화면에는 형광펜만 모은 그림을 쪽 위에 "곱하기"로 얹는다(종이는 형광펜 색이 되고, 그보다 어두운 글자와 펜은 그대로다). 그림 안에서는 불투명하게 그리므로 같은 자리를 여러 번 그어도 더 진해지지 않는다. 어두운 종이에서는 반대로 밝히는 방식으로 얹는다. 예전 버전에서 그은 형광펜도 같은 그림에 들어간다. 내보낸 PDF에는 아직 반투명한 색으로 들어간다(글자는 보이지만 화면보다 조금 흐리다).

곡선(0.9.0): 펜은 1초에 240번(손가락은 60~120번) 자리를 알려 온다. 보통 속도로 쓰면 화면에서 5~10픽셀마다 한 번이라, 그 자리들을 직선으로 이으면 곡선마다 모가 났다. 이제 알려 온 자리는 선의 매듭이고, 매듭 사이는 매듭들을 부드럽게 지나는 곡선(Catmull-Rom)을 1.5픽셀보다 촘촘한 점으로 풀어서 잇는다(`PenLine`). 가장 새 매듭까지의 구간은 다음 매듭이 와야 곡선이 정해지므로 그때까지는 임시로 그려 두었다가 다시 계산한다. 넘겨 주는 획의 점도 이 촘촘한 점이라 펜을 뗀 뒤에도 같은 모양이다. 또 하나는 선 둘레의 원이다. 쓰는 중인 선은 점마다 원을 놓고 그 사이를 띠로 이은 도형인데, 그 도형을 보여 주는 층(CAShapeLayer)이 원을 직선 몇 개로 바꿀 때 화면에 확대된 크기가 아니라 쪽의 1포인트 크기를 기준으로 삼아서, 곡선의 바깥쪽(원이 만드는 부분)이 각져 보였다. 원을 화면 배율에 맞는 수의 변을 가진 다각형으로 직접 만들어 넣는다(`InkPaint.shape`). 빌드 서버에서는 한 바퀴에 8·12·20번만 자리를 알려 준 동그라미가 둥글게 나오는 것을 확인했다. 아이패드에서 애플 펜슬로 쓴 선의 모습은 확인하지 못했다.

쓰는 중인 선(0.10.0, `WetInk`): 0.9.0까지 쓰는 중인 선과 아직 그림에 들어가지 않은 선은 도형 층(CAShapeLayer)으로 보여 줬다. 시스템이 그 층을 그리는 방식은 그림을 그리는 방식과 달라서, 쓰는 동안에는 곡선이 덜 매끄럽고 많이 확대하면 거칠었으며 펜을 뗀 뒤에야 깔끔해졌다. 이제 그 선들도 그림과 같은 코드로, 화면 픽셀에 맞춘 작은 타일(384픽셀)에 그린다. 선이 자라면 자란 부분이 걸친 타일의 그 부분만 다시 그린다. 그림이 그 선을 갖게 되면 타일에서 내리는데, 같은 모양을 같은 픽셀에 그린 것이라 화면에서는 바뀌는 것이 없다. 방금 쓴 선을 지우거나 실행 취소하면 그림을 기다리지 않고 타일에서 바로 내린다(0.9.0에서는 그림이 따라올 때까지 남아 있어서 지워지지 않은 것처럼 보였다). 필기를 처음부터 한 가지 방식으로 그리는 것이 다른 필기 앱들의 방식이고, 이 변경으로 쓰는 중과 쓴 뒤의 그리기가 하나가 됐다. 다 쓴 필기를 큰 그림 한 장으로 두는 것은 그대로다(쪽 전체가 한 장에 들어가는 배율에서는 스크롤해도 다시 그릴 일이 없다). 많이 확대했을 때는 보이는 부분만 그림으로 그리므로, 스크롤해서 그 밖으로 나가면 곧바로 새 그림을 청하고(전에는 다음 점검 때까지 기다렸다) 그동안 보이는 캔버스도 확대 배율 그대로 그리게 했다(전에는 8배까지).

도구 설정 창(0.10.0): 손에 든 도구를 한 번 더 누르면 뜨는 설정은 팝오버(내용 크기에 맞춰 스스로 크기를 정하는 별도 창)였다. 아이패드의 충돌은 "문서를 열고 펜을 눌렀을 때" 났고 스택은 그 창이 배치되는 자리였다. 이제 도구 막대 아래에 놓이는 보통 카드이고, 다른 곳을 누르면 닫힌다. 안의 색 격자도 필요할 때 칸을 만드는 격자에서 평범한 줄로 바꿨다. 아이패드에서 충돌이 없어졌는지는 확인되지 않았다.

글자 고르기(0.11.0, `TextPicker`): PDFKit에도 글자를 고르는 기능이 있지만 쓰지 않는다. PDFKit이 칠하는 선택 표시는 앱이 쪽 위에 올려 둔 그림 밑에 깔려 보이지 않고, 쪽에 필기를 받는 동안에는 그 제스처도 꺼져 있다. 그래서 쪽 덧씌움 위에서 직접 한다: 길게 누른 자리의 낱말은 PDFKit에 묻고(`selectionForWord`), 끄는 동안에는 쪽의 글자 상자를 한 번 읽어 둔 표에서 손가락과 높이가 가장 가까운 줄의 가장 가까운 글자를 찾는다. 고른 범위는 줄마다 상자 하나로 칠하고, 메뉴는 시스템의 편집 메뉴(`UIEditMenuInteraction`)다. 표시(AI 펜 자국) 위를 길게 누르면 전처럼 표시의 메뉴가 뜬다.

번역(0.11.0, `Translator`): 고른 글만 Claude Haiku 5.5로 보낸다. 이 모델은 따로 말하지 않으면 답하기 전에 생각을 하므로 `thinking`을 끄고 `effort`를 낮춰 곧바로 답이 나오게 했다. 설명에 쓰는 모델 설정과는 상관없고 문서 본문은 함께 가지 않는다. 한국어로 옮기며(설명 언어가 영어로 돼 있으면 영어로), 이미 그 언어인 글은 반대로 옮긴다. 한 번에 6,000자까지, 같은 글을 다시 고르면 기억해 둔 번역을 바로 보여 준다.

모양(0.11.0): 색을 하나로 줄였다. 앱의 색은 아이콘의 동그라미와 AI 펜 표시의 청록색 하나이고, 도구 막대에서 손에 든 도구는 색 대신 먹색으로 채운 칸으로 보인다(AI 펜만 청록색). 문서 탭은 칸을 칠하는 대신 밑줄을 긋는다. 서재의 큰 색 타일은 테두리만 있는 단추 줄로, 여섯 색으로 돌아가며 칠하던 폴더는 한 가지 색의 서류철 모양으로 바꿨고 문서 표지의 그림자를 줄였다. AI 기능마다 붙어 있던 반짝이 기호는 동그라미 안의 펜촉 기호로 바꿨다. 아이콘은 줄 친 종이 위에 손으로 그린 동그라미 하나다. 기준으로 삼은 것은 애플의 아이콘·도구 막대 지침(한눈에 알아볼 한 가지 모양, 작은 크기에서도 버티는 굵기, 색은 가장 중요한 동작에만)과, 내용이 주인공이고 도구는 물러나 있는 필기 앱들의 화면 구성이다.

열린 문서에 쪽 넣기(0.12.0): 빈 쪽은 PDF 옆의 목록(`pages.json`)에 적어 두기만 하지만, 다른 PDF의 쪽은 문서의 PDF 자체에 넣는다. 내보내기가 "원본 파일 + 덧붙임"으로 되어 있어서, 쪽이 다른 파일에 따로 있으면 내보낸 파일에 넣을 수 없기 때문이다. 넣을 때 PDFKit으로 저장하지 않는다(PDFKit은 쪽을 새로 그려 저장하고, 그렇게 쓴 파일에서는 일부 글꼴의 글자가 무슨 글자인지 사라진다). 문서 합치기에 쓰는 `PDFCopy`가 두 파일의 쪽을 객체째 그대로 옮겨 새 파일을 짜고(`PDFCopy.insert`), 원래 문서의 목차와 목차가 이름으로 가리키는 자리도 함께 옮긴다. 옆 목록의 빈 쪽들은 전에 서 있던 자리에 그대로 서도록 번호를 다시 적는다(`DocFile.relisted`). 원래 문서가 암호로 잠겨 그대로 옮길 수 없는 파일이면 넣지 않고 그렇게 알린다(새 문서로 가져오는 것은 된다). 들어오는 쪽의 파일만 읽을 수 없을 때는 그 파일만 PDFKit으로 다시 써서 넣는다. 화면에 떠 있는 문서에 넣을 때는 그 화면이 먼저 필기를 저장하고 물러난 다음 넣고, 문서를 새로 연다. 넣는 동안에는 화면을 건드릴 수 없다.

형광펜(0.12.1): 많이, 빠르게 그으면 밀리던 것. 형광펜 선은 폭이 14포인트쯤인데도 펜처럼 화면 점 절반 간격의 점마다 원판을 채워 그렸고(쓰는 동안), 형광펜 그림은 선이 하나 늘 때마다 그 쪽의 형광펜 전부를 처음부터 다시 그렸으며, 그림이 다 됐을 때 펜이 종이에 닿아 있으면 그 그림은 버렸다. 쉬지 않고 그으면 그림이 한 번도 올라가지 못해서, 아직 그림에 들어가지 못한 선이 화면에 계속 쌓였다. 이제 (1) 형광펜 선은 쓰는 동안에도 그림에서와 같이 "그 폭의 선 하나"로 그리고(`WetInk.asLines`), 폭의 7%보다 가까운 점은 건너뛴다(`InkPaint.thinned`), (2) 형광펜이 남기는 점 자체를 폭의 5% 간격으로 줄였고, (3) 형광펜 그림도 펜 그림처럼 바뀐 자리만 다시 그리며, (4) 펜이 닿아 있을 때 다 된 그림은 버리지 않고 두었다가 펜이 떨어지면 올린다. 빌드 서버는 같은 선 40개를 새 방식과 예전 방식(`-demoOldHighlighter`)으로 한 번씩 써 보고 걸린 시간을 `app-debug.log`에 적는다.

두 쪽씩 가로로 넘기기(0.12.1): 보기 방식의 네 번째. PDFKit의 쪽 넘김(가로로 한 쪽씩 넘기기에 쓰는 것)은 한 쪽씩만 보여 주므로, PDFKit의 "두 쪽"(이어지지 않는 두 쪽) 위에 넘기기를 직접 얹었다(`SpreadTurner`): 손가락을 왼쪽으로 쓸면 다음 두 쪽, 오른쪽으로 쓸면 앞의 두 쪽이 그쪽에서 밀려 들어온다. 펜은 넘기지 않고(쓴다), 손가락 필기가 켜져 있으면 쪽 위의 손가락도 넘기지 않는다(쪽 바깥 여백에서 쓸면 넘어간다). 확대한 상태에서는 쓸기가 화면을 옮기고, 더 옮길 수 없는 가장자리에서만 넘긴다. 손가락을 따라 쪽이 끌려오는 방식은 아니다. iPadOS 26부터는 화면 어디서든 오른쪽으로 쓸면 앞 화면으로 돌아가서, 0.12.1에서는 앞의 두 쪽으로 가려던 쓸기가 서재로 나가 버렸다(빌드 서버의 터치 시험에서 드러났다). 0.12.2부터 이 보기 방식에서는 그 동작을 끈다(화면 왼쪽 끝에서 쓸기와 뒤로 단추는 그대로다).

확대한 뒤 흐려지던 것(0.12.2): 실기기(iPadOS 27.2.1)의 진단 정보에 PDFKit의 배율(`scaleFactor`)은 0.97(화면 맞춤)인데 쪽은 화면에 4650포인트 폭, 곧 7.8배로 떠 있는 상태가 찍혀 있었다. 빠르게 축소했다가 확대한 뒤 PDFKit이 배율 값을 갱신하지 않았고 바뀌었다는 알림도 보내지 않은 것이다. 앱은 쪽 그림과 필기 그림, 캔버스의 정밀도를 모두 그 값에 맞춰 만들었으므로 0.97배용 그림이 7.8배로 늘어나 흐렸다. 이제 배율을 PDFKit에 묻지 않고 화면에서 잰다(`zoomSeen`: 쪽 덧씌움 위의 두 점이 쪽 보기에서 얼마나 떨어져 있는가). 초당 여덟 번의 점검에서 잰 배율이 캔버스 정밀도와 다르면 알림이 없었어도 맞춘다. PDFKit의 값과 잰 값이 다를 때는 진단 정보의 지난 동작에 "zoom seen 7.81, PDFKit says 0.97"처럼 남는다. 빌드 서버의 시뮬레이터에서는 두 값이 늘 같아서, 어긋난 상태 자체는 재현하지 못했다.

마지막으로 보던 곳(0.12.2): 문서마다 마지막으로 보던 쪽을 기억하고(`Library.notePage`), 화면에 떠 있던 문서가 무엇이었는지도 기억한다(`Library.showing`). 문서를 다시 열면 그 쪽에서 열리고, 앱을 다시 켜면 그 문서가 그 쪽에서 열린다. 서재로 나간 뒤 끈 경우에는 서재에서 열린다. 쪽 안에서의 위치와 배율은 기억하지 않는다(쪽 맨 위, 화면 맞춤). 빌드 서버의 화면 촬영과 터치 시험은 `-noRestore`로 실행해 늘 서재와 첫 쪽에서 시작한다.

쓰자마자 지우기(0.12.2): 방금 쓴 선이 지우개에 안 지워지는 일이 있었다. 재현하지 못했고, 코드에서 찾은 길은 하나다. 앱 자체의 펜과 지우개는 필기를 직접 바꾼 뒤 PencilKit 캔버스에 결과를 넘겨주는데, 캔버스는 넘겨받은 것을 "바뀌었다"고 되알려 온다. 그 알림이 늦게, 더 새 상태를 넘겨준 뒤에 오면 앱은 그것을 PencilKit이 스스로 바꾼 것으로 알고 필기 기록을 그 예전 상태로 되돌렸다. 그러면 방금 쓴 선은 화면에는 있는데 기록에는 없어서 지우개가 찾지 못한다. 이제 PencilKit이 스스로 바꿀 수 없는 때(캔버스에서 일하는 도구가 손에 없고, 캔버스에 닿은 지 4초가 넘었고, 실행 취소 직후도 아닐 때)에 오는 알림은 받지 않는다(`mayBeNews`). 줄 수가 다른 알림을 받지 않았을 때와 지우개가 아무것도 못 지우고 떨어졌을 때는 진단 정보의 지난 동작에 남는다("canvas told of …", "eraser met nothing …"). 또 "지우고 나면 이전 도구로"가 켜져 있을 때, 아무것도 못 지운 지우개질로는 도구가 돌아가지 않게 했다.

만년필(0.12.2): 필압 감도를 높이면 획 끝에 덩어리가 붙었다. 애플 펜슬은 종이에서 떨어지는 순간 힘을 0으로 알리는데, 앱은 0을 "힘을 알 수 없음(손가락)"으로 보고 보통 굵기로 그렸다. 가볍게 써서 가늘던 획이 마지막 점에서 보통 굵기로 불어난 것이다. 이제 펜슬의 0은 직전에 알려 온 힘으로 대신한다(`PenGesture.samples`). 그리고 만년필을 다른 필기 앱의 만년필에 가깝게 했다: 획의 처음과 끝이 뾰족해지고("펜끝 선명도", 기본 30%: 획 폭의 몇 배 거리에 걸쳐 굵기가 올라오고 내려간다; 점이나 아주 짧은 획은 그대로 둔다), 펜이 천천히 가면 조금 굵게, 빨리 가면 가늘게 나온다("속도 반응", 기본 35%: 화면에서 초당 150포인트 이하는 가장 굵게, 1500포인트 이상은 가장 가늘게). 둘 다 만년필 설정에서 0으로 내리면 전과 같다. 끝이 뾰족해지는 것은 펜을 뗄 때 정해지므로, 떼는 순간 획 끝 모양이 조금 바뀐다. 수치는 기기 없이 정한 것이다.

빠르게 많이 쓸 때 밀리던 것(0.12.3): 펜으로 획을 아주 빠르게 여러 개 그으면 선이 펜을 못 따라왔다. 실기기 진단 정보에는 4.1배로 확대한 93줄짜리 쪽과, 지우개를 든 직후 앱이 3초 동안 답하지 않은 기록이 있었다. 두 가지를 바꿨다. (1) 앱 자체의 펜이 획을 끝낼 때마다, 지우개가 획을 하나 지울 때마다 그 쪽의 필기 전체를 PencilKit 캔버스에 다시 넘겨주고 있었다. 캔버스는 보이지도 않는데(필기는 앱이 그린 그림으로 보인다) PencilKit은 넘겨받은 것을 배율만큼 곱게 전부 다시 그린다. 이제 캔버스는 "뒤처졌다"고만 적어 두고, 캔버스가 실제로 보이거나 쓰이게 될 때(PencilKit 도구를 들 때, 그림이 아직 없을 때)와 손이 1초 쉬었을 때 넘겨준다(`PageCanvas.behind`, `hand`). (2) 아직 그림에 들어가지 못한 선들과 지금 쓰는 선을 같은 타일에 그렸기 때문에, 펜이 움직일 때마다 그 자리를 지나는 대기 중인 선을 전부 다시 그렸다. 겹쳐 쓴 선이 많을수록 느려졌다. 이제 타일을 두 벌로 나눠, 펜이 움직일 때는 쓰는 선만 다시 그리고 획이 끝나면 대기 쪽에 한 번 그린다(`WetInk`). 빌드 서버는 겹쳐 쓴 40줄을 지금 방식과 예전 방식(`-demoEagerCanvas`)으로 써 보고 시간을 적는다.

화면을 다시 짬(0.15.0, 사용자가 시안을 보고 고름: 읽기 화면은 "시안 2", 서재는 "시안 A"): 사용자의 말은 "묘하게 구리고 묘하게 허전하다", "검정 자체는 좋은데 검정이 너무 많다", "상단 문서 바도 좁고 구분이 안 간다", 서재는 "폴더 액세스가 불편하다". 시안 그림은 `dist/ui-mockups/`(저장소 밖)에 있다.
- 읽기 화면: 시스템 내비게이션 막대(제목)를 숨기고 맨 위를 한 줄로 했다(`ReaderView.topBar`, 50pt). 왼쪽에 서재로 가는 화살표와 탭(`TabStrip`), 오른쪽에 그 문서의 단추들. 현재 탭은 위가 둥근 탭 모양으로 솟고 쪽수가 붙으며, 닫기(×)는 이름 뒤에 있다. 제목은 탭이 말하므로 따로 없다. 도구 막대는 자기 띠를 버리고 종이 위에 떠 있는 검정 알약이 됐다(`floatingBar`, 밝은 모드에서도 검정: 막대 안은 어두운 모드로 그린다). 왼쪽 끝 손잡이를 110pt 넘게 아래로 끌면 종이 아래쪽에 붙고(`toolBarLow`, 기억함) 위로 끌면 돌아온다. 도구 설정 카드, 알림, 번역 카드는 막대 위치에 맞춰 비켜난다. 막대가 위에 있을 때는 쪽 맨 위를 가릴 수 있다.
- 서재: 왼쪽에 자리 목록(모든 문서, 최근 본 문서, 질문한 문서, 폴더들, 새 폴더), 오른쪽에 고른 자리의 문서. 폴더는 더 이상 문서 사이의 카드가 아니고 들어갔다 나오는 화면도 없다. 문서를 폴더 줄에 끌어다 놓으면 들어가고 "모든 문서"에 놓으면 나온다. "모든 문서"는 폴더 안 문서도 다 보여 주고 이름 아래에 폴더 이름을 적는다. 맨 위 "이어서 보기"는 최근 문서 세 개와 읽은 데까지의 막대(마지막에 본 쪽 ÷ 전체 쪽). 질문 수는 문서 폴더의 `qa-*.json` 파일 수로 세어 청록 표시로 보인다. 화면 폭이 640pt 아래면 목록 대신 메뉴가 된다. 색은 `Tone`에 모았다(종이색 바탕, 검정은 고른 자리와 "추가" 단추에만).
- 건드리지 않은 것: 펜, 필기 그림, PDF 보기. 빌드만 확인했고 화면은 실기기에서 보지 못했다(이 변경은 시간에 따라 움직이는 부분이 적지만, 탭 줄의 가로 스크롤, 손잡이 끌기, 화면 회전, 분할 화면에서의 폭은 직접 봐야 한다).

서재를 덜어 냄(0.15.1): 0.15.0의 서재를 실기기(문서 17개, 폴더 6개)에서 본 사용자의 말은 "숨막힌다. 문서가 너무 많고 정신없다". 첫 화면 "모든 문서"가 폴더 안 문서까지 다 보여 줘서 폴더로 정리한 보람이 없었다. 정리안 셋 중 사용자가 1을 골랐다.
- 자리 목록 맨 위에 "홈"(`ShelfPlace.home`, 처음 뜨는 자리). 홈에는 "이어서 보기" 세 개(낮은 줄, 76pt, 읽은 데까지의 막대는 뺌)와 폴더에 넣지 않은 문서만 있다. 홈에서 찾기를 쓰면 모든 문서에서 찾는다. "모든 문서"는 그대로 남아 있다.

도구 막대 접기(0.15.2, 사용자의 요청: "안 쓸 때 숨기기"): 막대 왼쪽 끝 손잡이를 한 번 건드리면 막대가 접혀 종이 오른쪽 끝의 작은 알약(손잡이와 지금 쥔 도구 하나)이 되고, 그 알약을 건드리면 다시 펴진다(`toolBarFolded`, 기억함). 접혀 있어도 펜은 쥔 도구로 계속 쓰이고, 손잡이를 끌어 위·아래로 옮기는 것도 그대로다. 접힌 동안 실행 취소 단추는 보이지 않는다(두 손가락 두드리기 같은 대체 동작은 넣지 않았다). 빌드만 확인했고, 손잡이의 건드리기와 끌기가 실기기에서 서로 헷갈리지 않는지는 보지 못했다.

도구 막대가 스스로 접힘(0.15.3): 0.15.2를 본 사용자의 말은 "이런 게 아니라, 당장 필요없을 때 자동으로 접혔다가 도구를 바꿔야 할 때 나오게". 손으로 접는 것을 원한 게 아니었다.

- 펴짐: 접힌 알약 위에 애플 펜슬을 가까이 대면(호버, SwiftUI `onHover`) 건드리지 않아도 펴진다. 손가락이나 펜으로 건드려도 펴진다. 접힌 알약은 이제 막대가 있던 가운데에 남는다(펴진 막대가 펜 아래에 오도록). 호버로 펴진 뒤 0.45초 동안은 막대가 건드림을 삼킨다: 알약을 누르려고 내려오던 펜이 엉뚱한 도구를 고르지 않게.
- 끄기: 읽기 화면 ⋯ 메뉴의 "쓰는 동안 도구 막대 접기"(`toolBarAuto`, 기본 켬).
- 꽉 쥐기·두 번 두드리기로 도구를 바꿀 때는 펴지 않는다(사용자는 쥐고 바로 쓴다).
- 미확인: 호버가 실기기에서 SwiftUI `onHover`로 오는지(빌드 서버에는 펜슬이 없다), 0.45초가 맞는지, 접히는 움직임이 다음 획과 겹칠 때 거슬리는지.

접기를 버리고 밀어서 닫기로(0.15.4): 0.15.3을 두고 사용자가 한 말은 "이건 빼자. 수동으로 위로 밀어서 닫을 수 있게 하고, 필기 외 다른 동작을 하거나 닫은 쪽을 다시 끌어내리면 나오게 하자. 전체적인 도구 바 사이즈를 줄여줘". 0.15.2의 작은 알약과 0.15.3의 스스로 접힘·호버 펴짐은 모두 뺐다(`ReaderView.swift`, `PDFInkView.swift`를 0.15.1로 되돌린 뒤 고침; `toolBarFolded`, `toolBarAuto`, `onWrote`는 이제 없다).
- 닫기: 손잡이를 막대가 붙어 있는 가장자리 쪽으로(위에 있으면 위로, 아래에 있으면 아래로) 24pt 넘게 밀면 막대가 그 가장자리 너머로 사라지고 짧은 손잡이 줄(`barTab`)만 남는다(`toolBarHidden`, 기억함). 반대쪽으로 110pt 넘게 끄는 것은 전처럼 위·아래를 바꾼다.
- 열기: 남은 손잡이 줄을 안쪽으로 끌거나 건드리면 나온다. 필기가 아닌 동작에도 나온다: 펜슬 꽉 쥐기·두 번 두드리기, 쪽이 바뀜, 확대·축소(`ReaderController.onZoom`). 왜 나왔는지는 진단 기록에 "tool bar back: …"으로 남는다.
- 크기: 막대 높이 52 → 44pt, 도구 단추 44×42 → 38×36, 도구 설정 칸 304 → 268pt, 색 동그라미 23 → 20pt. 막대가 좁아져서 도구 설정 칸은 화면 폭 700pt부터 보인다(전에는 790).
- 미확인(빌드만 함): 필기 중에 확대 신호가 저절로 와서 막대가 튀어나오지 않는지(iPadOS 27은 배율 값이 어긋난 적이 있다; 그러면 기록에 "tool bar back: zoom"이 남는다), 이어 보기에서 쓰면서 스크롤할 때 쪽이 바뀌어 막대가 나오는 것이 거슬리는지, 작아진 단추가 누르기에 충분한지.

닫기도 뺌(0.15.5): 사용자의 말은 "툴바는 그냥 건드리지 말자. 툴바 사이즈 변경 빼고 롤백". 0.15.4의 밀어서 닫기와 스스로 나오기를 뺐다(`toolBarHidden`, `barTab`, `showBar`, `onZoom`은 이제 없다). 도구 막대는 0.15.1의 동작(손잡이를 끌어 위·아래로 옮기기만) 그대로이고, 0.15.4의 작아진 크기만 남았다. 0.15.2~0.15.4의 위 기록은 지나간 시도의 기록이다. `PDFInkView.swift`는 0.15.1과 같다.

짧은 획이 펜을 뗄 때 커지던 것(0.15.6): 사용자가 "획을 그리고 나서 크기나 굵기가 변한다"고 한 것이 짧은 획에서 두드러진다고 확인해 주었다. 원인은 코드에 그대로 있었다: 쓰는 동안에는 모든 획이 뾰족한 시작(`tip`배 굵기)에서 굵어지는 모양으로 보이는데, 떼는 순간 길이가 `tipReach`보다 짧으면 전체를 펜 굵기로 채웠다(0.5mm·선명도 25%에서 23% 굵어짐, 50%에서 60%, 90%에서 3배). 이제 매듭에는 펜이 만든 굵기만 두고(`bare`), 끝의 뾰족함은 `PenLine.dress`가 입힌다. 길이가 `turn`(= `tipReach`) 이하인 획은 쓰는 동안에도 펜 굵기 그대로(그 획에서 가장 굵었던 값 `peak`) 보이고 떼어도 변하지 않는다. 길이가 `turn`에서 그 두 배로 가는 동안 시작이 서서히 뾰족해지고(`grown`), 떼는 순간의 끝 다듬기도 같은 비율로만 한다. 두 배 이상인 획은 쓰는 중에도 뗀 뒤에도 0.15.5와 같다(끝은 여전히 떼는 순간 다듬는다; 0.14.1처럼 쓰는 중에 끝을 가늘게 보이지는 않는다). 길이 1~2배 사이의 획은 다 쓴 모양이 전보다 조금 굵다(전에는 길이가 `tipReach`를 넘는 순간 통통한 획이 양끝이 깎인 획으로 한 번에 바뀌었다). 시작이 굳기 전(`startFirm`이 거짓)에는 쓰는 중인 선을 아래 타일로 넘기지 않는다; 보통 굵기에서는 그 구간이 점 스무 개 안쪽이다. 계산은 파이썬으로 옮겨 확인했다(짧은 획: 쓰는 중 = 뗀 뒤, 긴 획: 전과 같음, 길이에 따른 모양 변화에 계단 없음). 미확인(빌드만 함): 획을 시작한 직후 펜촉 밑에서 시작이 가늘어지는 것이 눈에 띄는지, 점이 전과 같은 크기로 느껴지는지(필압 감도가 높으면 점은 이제 뗄 때의 굵기가 아니라 가장 굵었던 값이다).

시작점을 다시 그리지 않음(0.15.7): 0.15.6을 쓴 사용자의 말은 "긴 획을 그릴 때 시작점이 변하는 게 눈에 보여". 펜촉에 가려질 것이라는 0.15.6의 짐작이 틀렸다. `bare`·`dress`·`startFirm`을 뺐고 `AppPen.swift`와 `WetInk.swift`는 0.15.5에서 다시 시작했다. 이제 규칙은 하나다: 화면에 한번 보인 선은 쓰는 동안 다시 그리지 않는다. 떼는 순간과 시작점을 둘 다 건드리지 않으려면 짧은 획은 쓰는 동안 보인 그대로 남을 수밖에 없다.
- 쓰는 동안: 0.15.5와 같다(시작은 뾰족하게 올라오고 한번 그린 점은 그대로).
- 떼는 순간: 길이가 `tipReach` 이하인 획은 아무것도 바꾸지 않는다(전의 채우기를 없앰). 그 두 배까지는 끝 다듬기를 길이에 비례해 조금만 하고(`grown`), 두 배 이상은 0.15.5와 같다.
- 점: 펜이 닿은 자리에서 거의 움직이지 않으면(화면 기준 초당 60포인트 미만) 그 머문 시간(`dwell`)만큼 뾰족한 시작을 지난 것으로 친다(`lingered`, 0.05초면 펜 굵기). 매듭이 아직 하나뿐인 동안에는 그 첫 매듭이 펜 아래에서 굵어진다(줄지는 않는다). 그래서 톡 찍은 점은 펜 굵기에 가깝고 뗄 때 변하지 않는다. 움직이는 획에서는 머문 시간이 0이라 0.15.5와 같다.
- 달라지는 것: 빠르게 그은 짧은 삐침(쉼표 등)은 떼어도 채워지지 않아 0.15.5보다 가늘게 남는다(선명도 25%에서 시작이 0.81배, 선명도가 높을수록 더).
- 미확인(빌드만 함): 점이 머무는 동안 굵어지는 것이 눈에 띄는지, 0.05초와 초당 60포인트가 맞는지, 짧은 삐침이 너무 가늘지 않은지.

획 끝의 혹(0.15.8): 0.15.7을 쓴 사용자가 "좀 나아지긴 했는데 묘하게 아쉽다"며 굿노트와 이 앱에 같은 글씨를 쓴 화면 녹화와 테스트 기록을 주었다.
- 녹화(프레임 단위): 굿노트는 펜을 떼는 프레임에서 끝의 테두리 한 겹(6~20픽셀)이 사라질 뿐 새 잉크가 생기지 않는다. 이 앱은 떼는 프레임 12개 중 11개에서 한쪽 10픽셀이 사라지고 다른 쪽에 10~15픽셀이 생겼다: 끝이 옆으로 옮겨 가며 작은 혹이 붙는다.
- 기록(37획의 펜 샘플): 터치가 끝났다고 알려 오기 전 마지막 12.5ms(샘플 3개, 중앙값) 동안 펜슬의 진짜 힘은 이미 최대의 3% 아래다. 종이에서 떨어지는 중인 그 구간에 펜촉은 중앙값 0.44, 최대 1.31 쪽 포인트를 더 움직이고, 그중 옆으로 벗어난 것이 중앙값 0.25, 최대 1.15다(배율 2.89에서 화면 3~7픽셀). 세로획 끝에서 되돌아 올라가거나 옆으로 꺾인다. 그 구간의 진짜 힘은 터치가 끝날 때 아직 모른다(2~35ms 뒤에 온다; 그때 알려진 추정값은 0.1~0.2로 높다).
- 고침: 펜을 떼면 마지막 12.8ms(획 길이의 4분의 1을 넘지 않게)에 들은 자리와 그것으로 만든 매듭을 획에서 뺀다(`PenLine.leave`, `liftOff`). 획 안정화의 간격도 그 전의 자리까지만 잇는다. 같은 37획에 대어 보면 떨어진 뒤의 옆 이동이 중앙값 0.00, 최대 0.26으로 준다. 쓰는 동안은 그대로이고, 떼는 순간 끝의 그 부분이 사라진다(굿노트처럼 줄기만 한다). 모든 도구의 획에 적용된다; 뗀 뒤 다시 그리는 것(`afresh`)도 이제 모든 획에서 한다.
- 미확인(빌드만 함): 실기기에서 혹이 사라졌는지, 빠르게 날려 쓴 획의 끝이 짧아 보이지 않는지(잘리는 길이는 날린 획에서 최대 0.4 쪽 포인트였다).

GPU를 화면까지(0.18.0, 사용자의 말: 0.17.0을 써 보고 "체감 차이는 없는데?", 이어서 되가져오기 없애기와 쓰는 중인 선을 GPU로 하는 것 둘 다 "해봐", "바로 컴파일하고, 내가 실사용으로 확인할거야"):
- 0.17.0의 실기기 기록: 필기 그림 한 장(3705 x 2779, 1~29획)이 28~34ms였고 그중 그리기 7~11ms, 메모리로 되가져오기 14~21ms. 이 그림은 펜을 떼고 0.45초쯤 뒤에 눈에 안 보이게 바뀌므로 체감이 없는 것이 맞았다.
- 필기 그림: GPU가 화면이 그대로 받는 표면(IOSurface)에 그리고 그것을 레이어에 올린다(`InkGPU.surfaces`, `PagePicture.show(straight:)`). 되가져오기가 없다. 표면을 못 얻으면 0.17.0의 방식, 그것도 안 되면 CPU. 시뮬레이터에서는 이 길을 쓰지 않는다. 기록에는 "drawn whole by the GPU for the screen (lines …, drawing …, nothing brought back)".
- 쓰는 중인 선과 그림을 기다리는 선(`WetInk`): 보이는 부분을 덮는 Metal 레이어 하나에, 펜이 움직일 때마다 모든 선을 통째로 다시 그린다. 조각으로 자르지 않고 타일도 없다. 앱이 화면에 올리는 다른 변경과 같은 순간에 올라가도록 했다(`presentsWithTransaction`; 그림으로 넘어가는 순간에 선이 빠졌다 들어오지 않게). 설정 → "쓰는 중인 선도 GPU로"(기본 켬)를 끄면 0.17.0까지의 타일 방식이다. 기록에는 획마다 "pen: shown by the GPU n times, … ms of the main thread each on average, … at most".

- 방식: 획의 점과 점 사이 한 토막을 숫자 여섯 개(양 끝 자리와 양 끝 반지름)로 넘기고, 셰이더가 픽셀마다 그 토막(양 끝이 둥근 모양)까지의 거리를 계산해 덮인 정도를 낸다. CPU에서 삼각형이나 도형을 만들지 않고, 배율이 바뀌어도 넘기는 숫자는 같다(숫자는 획마다 보관한다, `Kept`). 한 획의 토막들은 서로 겹치므로, 같은 색 획들을 먼저 "픽셀이 얼마나 덮였나" 그림에 최댓값으로 모은 다음 그 색으로 한 번에 칠한다(가장자리가 두 번 칠해져 짙어지지 않게). 서로 닿지 않는 획은 순서를 바꿔 같은 색끼리 묶는다(`Batch`의 32×32 칸). PencilKit이 그려야 하는 획(연필, 부분 지우개로 자른 획)은 PencilKit의 그림을 받아 순서대로 끼운다. 결과는 `InkPaint.Made`와 같은 CGImage라서 화면에 올리는 경로, 펜을 뗄 때의 넘겨주기, 쓰는 중인 선(`WetInk`, Core Graphics)은 전혀 바뀌지 않았다.

- 확인: 빌드 서버 시뮬레이터에서 견본 docx·pptx·xlsx·epub이 PDF로 바뀐 것과 그 쪽 그림(Actions의 `convert` 입력; `tools/make_samples.py`). 미확인: 실기기, 실제 강의 자료, 옛 형식(.doc/.ppt/.xls), 큰 책의 변환 시간, EPUB 원본 보기 화면(그림을 찍지 않았다), 넓은 엑셀 시트가 인쇄 폭에 맞춰지는지.

획 시작의 둥근 점이 다시 가늘어지던 것(0.15.9): 0.15.8을 쓴 사용자가 "펜끝 선명도를 좀 올리면 끝이 엄청 가늘어져", 이어서 "l의 끝을 봐. 상단 끝"이라고 했다. 처음에는 획의 끝(뗄 때의 다듬기)으로 잘못 읽었다. 녹화를 순서대로 읽으니(프레임 번호로 건너뛰어 읽으면 이 녹화에서는 엉뚱한 프레임이 온다) world의 l이 둥근 점으로 시작했다가 두 프레임 뒤에 윗끝이 깎인 모양으로 바뀌어 남았다. 0.15.7의 버그다: 머문 점은 매듭이 하나뿐인 동안 펜 굵기로 자라는데, 둘째 매듭이 생긴 뒤 펜슬의 진짜 힘이 늦게 오면 `correct`가 첫 매듭의 굵기를 맨 끝(`pointed(0)`, 선명도 30%에서 0.78배)에서 다시 셈해 줄여 버렸다. 선명도가 높을수록 많이 준다. 이제 첫 매듭이 자랄 때 그 자리의 기록(`Heard.run`)에 머문 만큼(`lingered`)을 적어 두고, `correct`는 그 값으로 센다. 미확인(빌드만 함): 실기기에서 획의 윗끝이 둥글게 남는지. 사용자가 고르기 전이라 뗄 때의 끝 다듬기는 손대지 않았다(0.15.8의 녹화에서 뗄 때 22~46픽셀이 깎였고 굿노트는 6~20픽셀이었다).

암호 없이 열리는 문서의 인쇄·복사 제한도 내보낼 때 풂(0.14.13, `Exporter.everything`, 사용자 요청): 제한만 걸린 PDF는 앱 안에서는 그대로 쓰이고, 내보낼 때 PDFKit으로 다시 쓰면서 원본의 제한을 옮겨 적고 있었다. 이제 모든 권한을 허용으로 적는다. 가져온 파일 자체는 건드리지 않는다(PDFKit으로 다시 쓰면 일부 글꼴의 글자 정보가 사라질 수 있어서 내보낼 때만 한다). 실기기 확인 전.

암호를 풀어 가져온 사본의 제한도 풂(0.14.12): 0.14.11은 사본에 원본의 인쇄·복사 제한을 남겼고 안드로이드(0.15.3)는 모두 뺐다. 사용자가 아이패드도 풀어 달라고 해서, 사본을 다시 잠글 때 모든 권한을 허용한다(`PDFAccessPermissions` 전부). PDFKit은 잠겨 있던 문서를 아예 암호화 없이 쓰지 못해서 "아무도 모르는 소유자 암호 + 제한 없음"으로 쓴다. 내보내기(`Exporter`)가 암호 없이 열리던 문서의 제한을 유지하는 것은 그대로다. 실기기 확인 전.

암호가 걸린 PDF 가져오기(0.14.11, `Library.copy(_:to:password:)`, `LibraryView.openLocked`): 열 때 암호를 묻는 PDF는 PDFKit에서 풀기 전까지 쪽수가 0이라 "이 파일은 열 수 없어요"로 거절됐다. 이제 가져올 때 암호를 묻는다(여러 개면 하나씩). 앱은 문서 파일을 열 군데 넘는 곳에서 암호 없이 그대로 여는 구조라, 암호는 가져올 때 한 번만 쓰고 암호 없이 열리는 사본을 보관한다. 사본은 내보낸 사본과 같은 방식으로 다시 잠근다(원래의 인쇄·복사 제한은 그대로, 아무도 모르는 소유자 암호). 암호는 저장하지 않고 기록에도 남기지 않는다. 사본이 암호 없이 열리고 쪽수가 같은지 확인하고, 아니면 가져오지 않는다. 이미 열린 문서에 쪽을 끼워 넣는 경로는 그대로다(암호 걸린 파일은 새 문서로 가져온 뒤 합쳐야 한다). 실기기 확인 전: PDFKit이 사용자 암호로 푼 문서를 이 옵션으로 다시 쓰면 암호 없이 열리는지는 빌드 서버에서 확인하지 못했다.

실험 모드를 뺌, 펜은 0.14.5 그대로(0.14.10): 0.14.9를 쓴 사용자가 "더 이상해졌다. 펜은 원복하자"고 했다. `PenLine.plain`과 설정의 스위치를 모두 뺐고 `AppPen.swift`, `InkModel.swift`, `ReaderView.swift`, `PDFInkView.swift`는 0.14.6과 같다(펜 동작은 0.14.5 = 0.14.0, 테스트 기록의 펜 샘플은 남김). 아래 0.14.7~0.14.9 항목은 기록으로만 남긴다. 거기서 얻은 것 가운데 다시 쓸 만한 사실: 펜을 뗄 때 힘은 약 0.04초에 걸쳐 0으로 빠진다, 닿는 순간 약 0.02초는 임시값 0.333이 온다, 평소 글씨의 힘은 0.13~0.45로 날마다 다르다, 마지막 0.03초의 진짜 힘은 뗀 뒤에 온다. 필압을 그대로 그리는 방식은 날린 획의 끝은 굿노트와 비슷했지만 글자 획에서는 끝이 급하게 가늘고 시작이 몸통보다 굵어서 세 번 고쳐도 받아들여지지 않았다.

실험 모드의 끝이 여전히 급하게 가늘어짐(0.14.9): 0.14.8(선명도 25%, `slope` 0.23)의 스크린샷에서 글자 획은 16→14→12→10→8px로 끝이 여전히 절반이었다. 사용자: "여전히 끝 부분으로 가면 급격하게 가늘어져." 그날은 힘이 더 가벼워서(0.13~0.18) 힘이 빠지는 구간이 쪽 좌표로 1.3pt였고, 0.23의 기울기로는 그 안에서 0.3pt(굵기의 20% 이상)가 줄 수 있었다. 이제 제한은 화면 거리 기준이다: 화면 1pt를 갈 때 굵기의 `slope`배보다 많이 줄지 못한다. `slope` = 0.004 + 0.032 × 펜끝 선명도(25%에서 0.012). 손이 하는 일은 배율과 무관하므로 끝 모양도 배율과 무관해진다. 2026-11-22 첫 기록으로 계산(0.012): 글자 획 끝 0.80~0.97, 날린 획 끝 0.59~0.77. 남는 것: 가볍게 쓰면 시작(펜슬의 임시값 0.333)이 몸통보다 굵다(16px 대 13px). 실기기 확인 전.

실험 모드의 끝이 글자에서 너무 얇음(0.14.8, `PenLine.slope`): 0.14.7을 실기기에서 쓴 결과 스크린샷의 굵기는 계산대로였다(설정 16.1px, 날린 획 16.8→10~11.6px, 글자 획 끝 8px, 점 17~19px). 사용자: "가에서 ㅏ를 보면 끝이 너무 얇아." 기록을 보면 그 세로획은 끝 5.5pt(화면) 구간에서 16→7px로 줄었다. 힘이 빠지는 시간은 같은데 글자 획은 그동안 간 거리가 짧아서 급한 꼬리가 된다. 이제 실험 모드에서 굵기는 선을 따라 1pt 갈 때 `slope`pt보다 빨리 줄지 못한다(매듭을 만들 때와 힘이 정정될 때 모두; 굵어지는 쪽은 제한 없음). `slope` = 0.1 + 0.5 × 펜끝 선명도(사용자 설정 30%에서 0.25). 2026-11-22 첫 기록으로 계산: 0.25에서 날린 획 끝은 0.58~0.73 그대로, 글자 획 끝은 0.5 안팎에서 0.76~0.85로, 멈췄다 뗀 획은 가늘어지지 않는다. 실기기 확인 전.

실험: 필압 그대로 그리는 만년필(0.14.7, `PenLine.plain`, 설정의 "실험: 필압 그대로 그리기", 기본 꺼짐): 0.14.6의 기록(62획, 2026-11-22)에서 나온 것을 따른다. ① 펜을 뗄 때 힘은 획의 종류와 무관하게 약 0.04초(중앙값 38ms, 25~75ms)에 걸쳐 0으로 빠진다. 날린 획은 그동안 화면 40~80pt를 가서 끝이 길게 가늘어지고, 글자 획은 4~5pt라 짧게 뾰족하고, 멈췄다 떼면 뭉툭하다. 굿노트 스크린샷의 세 모양과 같다. ② 닿는 순간 펜슬은 약 0.02초 동안 임시값(0.333)을 알려 주고 진짜 힘(0.05~0.25에서 약 0.05초에 걸쳐 오름)은 뒤에 정정한다. ③ 평소 글씨의 힘은 0.2~0.45(최대 4.17의 5~10%)라서, 0.14.3의 "0.35 아래면 가늘게"는 글씨 쓰는 내내 걸렸다. 켜면: 굵기 = 설정 굵기 × (필압/0.22)^γ, 필압 = clamp(0.5·ln((M−2)f+1)/ln(M−1), 0.025, 1), γ = 0.38 + 0.19 × 필압 감도(`PenLine.nib`; γ의 양 끝은 굿노트 민감도 최소·최대에서 잰 굵기 12→21.6px, 10→24px에 맞춘 가설이고, 힘과 굵기를 같은 획에서 잰 것은 아니다). 위치로 끝을 다듬지 않고 속도도 쓰지 않는다. 시작 0.06초는 처음 들은 힘 아래로 내려가지 않게 해서 시작이 가늘어지지 않는다. 정정된 힘은 펜보다 약 0.025초 늦게 오므로 그 힘을 기다리는 매듭은 굳히지 않는다(`sure`, 0.12초 넘으면 포기). 마지막 0.03초 분량의 진짜 힘은 펜을 뗀 뒤에야 오므로, 떼는 순간 마지막으로 확인된 힘에서 0까지 고르게 빠진 것으로 친다(`fallAway`, 끝의 최대 14샘플). 즉 끝의 4~80pt는 떼는 순간 확정된다. 기록된 샘플로 파이썬에서 계산한 굵기(설정 굵기 대비): 날린 획 1.03→끝 0.58~0.73(굿노트 10→5.6px), 글자 획은 끝 5~10%에서만 0.5 안팎으로, 멈췄다 뗀 획 끝 0.75~0.89, 세게 누른 선 최대 1.7~1.8. 굿노트는 날린 획이 더 일찍부터 가늘어지는데(속도 항 추정) 넣지 않았다. 실기기 확인 전.

펜 샘플 기록(0.14.6, `PenGesture.tellNotes`): 펜 동작은 0.14.5 그대로이고, 테스트 기록이 켜져 있을 때만 획마다 펜슬이 알려 준 값(첫 샘플부터의 ms, 쪽 좌표, 힘, 최대 힘, 고도각, 방위각, 힘이 아직 추정값이면 `~번호`)을 모아 펜을 뗀 뒤 한 덩어리로 적는다. 나중에 확정된 힘은 `= 번호 힘`으로 덧붙는다. 펜을 내릴 때 펜 종류와 설정(굵기, 필압 감도, 펜끝 선명도, 속도 반응, 획 안정화)도 한 줄 적는다. 쓰는 중에는 배열에 넣기만 하고 글로 바꾸는 일은 펜을 뗀 뒤 다른 스레드에서 한다. 용도: 굿노트 만년필의 굵기를 스크린샷으로 잰 값(시작 테이퍼 없음, 날린 획은 전체에 걸쳐 10→5.6px로 서서히 가늘어지고 뭉툭하게 끝남, 점은 10px 안팎으로 일정, 민감도 최소에서 12→21.6px·최대에서 10→24px)과 맞출 식을 정하려면 같은 획에서 손이 실제로 내는 힘과 속도를 알아야 한다. 굿노트의 힘→필압 변환은 `0.5·ln((M−2)f+1)/ln(M−1)`, 0.025~1로 자름(바이너리 분석 보고, 검산함: f=1에서 0.5, f=M에서 1)이라고 하나 필압→폭 식은 미확인이다.

오늘의 펜 변경을 되돌림(0.14.5): 0.14.1(쓰는 중에도 끝을 가늘게), 0.14.3(끝을 필압만으로), 0.14.4(속도 반응을 굿노트 측정값에 맞춤)와 만년필 설정의 순서·스위치 변경을 사용자가 "필기감이 더 어색해졌다"며 되돌리라고 했다. `AppPen.swift`, `WetInk.swift`, `ReaderView.swift`는 0.14.0과 같고, 만년필은 다시 펜을 떼는 순간 끝을 다듬는다. 남긴 것은 버그 수정이다: 쪽별 배율(0.14.0), 번역 지침(0.14.0), AI 펜 자동 선택해제(0.14.0), 배율 1 미만에서 쓰는 선의 해상도(0.14.2), 진단 기록. 아래 세 항목은 기록으로만 남긴다.

만년필을 굿노트 화면에 맞춰 봄(0.14.4): 사용자가 같은 글씨("hello world!", 가로선 둘, 점 일곱)를 두 앱에 쓰고 찍은 화면을 쟀다(둘 다 펜끝 선명도 25%, 필압 최소, 획 안정화 10%; 쪽 배율은 이 앱이 1.19배 큼). 굿노트: 글자 획 굵기 10~13픽셀, 빠르게 그은 선은 9.3에서 5.8로 점점 가늘어짐(−38%), 점은 획 굵기와 비슷(10~13). 이 앱: 어디나 16픽셀(10·90분위가 같음), 점 15~18. 차이는 속도에 대한 반응이었다: 전에는 화면 기준 초당 150포인트부터 1500포인트까지에서 최대 17% 가늘어졌고, 손글씨 속도(수백)에서는 4%도 안 됐다. 이제 100~1200에서 `0.25 + 0.5 × 펜끝 선명도`만큼(25%에서 37.5%) 가늘어진다. 가벼운 필압에서 줄어드는 폭도 키웠다(`tip` = 1 − (0.3 + 0.6 × 선명도), 25%에서 0.55; 기준 필압 8.5% → 12%). 굵기는 여전히 펜이 그 자리에 있던 순간의 값으로만 정해지고 뒤에 바뀌지 않는다. 표본이 화면 한 장이라 수치는 어림이고, 실기기 확인 전.

획 끝은 필압만으로(0.14.3, `PenLine.pointed(under:)`): 0.14.1의 "쓰는 중에도 끝을 가늘게"는 펜 바로 뒤의 선이 쓰는 내내 가늘어졌다 굵어져서 사용자가 "너무 거슬린다"고 했다(그 방식이 굿노트의 것이라는 말은 근거 없는 추정이었다). 이제 선의 굵기는 펜이 그 자리에 있을 때의 필압과 속도로만 정해지고, 한번 그린 점은 다시 건드리지 않는다. 위치로 양 끝을 다듬던 것(시작의 `pointed(run)`, 끝의 `tipReach`)은 없앴다. 대신 필압이 `lightTouch`(펜슬 최대 힘의 8.5%, 보통 터치의 3분의 1쯤) 아래로 내려가면 굵기가 `tip`(= 1 − 0.75 × 펜끝 선명도)까지 줄어든다. 펜이 닿고 떨어질 때 힘이 잠깐 약한 것이 그대로 뾰족한 끝이 된다. 힘을 준 채 멈추고 떼면 끝은 뭉툭하다. 닿고 아직 움직이지 않은 펜 아래의 점은 힘이 실리는 대로 커진다(전에는 뗄 때 채웠다). 손가락처럼 필압이 없으면 끝은 다듬어지지 않는다. `lightTouch`와 줄어드는 정도는 실기기에서 맞춰야 하는 값이고 확인 전이다. 떼는 순간 남는 변화는 획 안정화가 남긴 간격을 잇는 것뿐이다.

쓴 뒤 굵기가 변해 보인다는 보고가 0.14.1에서도 이어짐(0.14.2, 추정 수정): 쓰는 중인 선의 해상도(`fineness`)가 배율이 1 미만이어도 화면의 2픽셀/포인트 아래로 내려가지 않았다. 사용자의 기록에는 배율 0.71, 0.92, 0.97로 쓴 구간이 있다(질문 패널을 열었거나 쪽이 화면보다 클 때의 맞춤 배율). 그때 선은 2픽셀/포인트로 그려져 1.4로 줄어 보이고, 0.4초 뒤 1.4로 직접 그린 필기 그림이 넘겨받는다. 가는 선에서 그 차이가 굵기 변화로 보일 수 있다. 이제 `fineness`는 배율 그대로다(하한 0.25). 이것이 사용자가 본 변화의 원인인지는 확인되지 않았다. 테스트 기록의 "pen: shown at … pixels a point while written"과 뒤따르는 "ink picture: … at … pixels a point"가 같은지로 가린다.

만년필·붓의 획 끝을 쓰는 중에도 뾰족하게(0.14.1, `PenLine.tipEnd`): 0.14.0까지는 펜이 닿아 있는 동안 획 끝을 쓰던 굵기 그대로 그리고, 떼는 순간 끝에서 `tipReach`만큼을 가늘게 다듬었다. 획마다 떼는 순간 모양이 변했고, 짧은 획은 전체가 변했다(`tipReach`보다 짧으면 반대로 전체를 굵게 채웠다). 사용자가 "펜을 쓰고 나서 필기의 크기나 두께가 변한다"고 한 것의 후보다. 이제 쓰는 동안에도 지금의 끝에서 `tipReach`만큼을 같은 식으로 가늘게 보여 주고, 펜이 나아가면 그 자리는 원래 굵기로 돌아간다(굿노트·노타빌리티의 만년필이 보이는 방식). 떼는 순간에는 같은 계산을 한 번 더 할 뿐이라 획 안정화가 남긴 간격을 잇는 것 말고는 변하지 않는다. 길이가 `tipReach` 이하인 획은 전체가 펜 굵기이고, 거기서 두 배 길이까지 양 끝이 서서히 생긴다(전에는 그 경계에서 한 번에 바뀌었다). 가늘게 보이는 끝 구간은 아직 굳지 않은 것으로 쳐서(`PenLine.firm`) 타일에 굽지 않는다. 설정은 굿노트 만년필의 순서를 따랐다: 펜끝 선명도, 필압 감도, "쓰는 속도에 따라 굵기 조절" 스위치(전의 속도 반응 슬라이더; 켜면 0.35), 획 안정화. 계산은 파이썬으로 옮겨 확인했고 실기기 확인 전.

확대해도 쪽과 필기가 흐린 채 남던 것(0.14.0, 원인 확인): 사용자의 테스트 기록에 "zoom 1.4995"와 "page 4: 720 x 540 points, on screen 7200 x 5400; 2 pages laid out"이 함께 있었다. 쪽은 화면에 10배로 서 있는데 앱은 1.5배로 알고 있었다. 쪽을 한 장씩 넘기는 보기에서 PDFKit은 옆 쪽도 깔아 두는데, 쪽마다 스크롤 뷰가 따로라 옆 쪽은 화면 맞춤 배율에 서 있다. `zoomSeen`은 깔린 쪽 중 사전 순서로 먼저 나오는 쪽의 배율을 쟀고, 그게 옆 쪽이면 보이는 쪽의 그림과 필기가 그 배율로 그려져 늘어났다. 사전 순서는 문서를 다시 열어야 바뀌므로 그때까지 남았다(정상이던 기록들은 "1 pages laid out"이거나 순서가 맞은 경우). 이제 `zoomSeen`은 화면을 가장 많이 차지한 쪽의 배율이고, 쪽 그림과 필기 그림은 쪽마다 자기 배율(`zoom(of:)`)로 그린다. 진단 정보에 깔린 쪽마다의 배율이 한 줄 더 나온다. 실기기 확인 전.

번역 지침(0.14.0): 낱말 하나("investigation")나 구("all identical in structure")를 고르면 번역 대신 되묻거나 대답했다. 고른 글을 `<고른_글>` 태그에 담아 보내고, 지침에 "대화 상대가 아니라 번역기", 되묻기·대답·자기 설명 금지, 예시 넷을 넣었다. 실제 모델 응답은 확인 전(빌드 서버는 대역 서버를 쓴다).

AI 펜도 "한 번 묻고 나면 이전 도구로 돌아가기"(0.14.0, `InkChoice.aiAuto`): AI 펜 줄의 설정 단추에서 켠다. 기본은 꺼짐.

확대 뒤 다시 그리기가 가끔 멈춘다는 보고(0.13.9, 원인 미확인): 0.13.7 실기기에서 간헐적으로 확대해도 그림이 배율에 맞춰 다시 그려지지 않는다고 했다. 함께 온 진단 정보 두 개는 모두 그림이 배율과 같은 상태에서 찍혀 원인을 말해 주지 않았고, 코드에서도 확실한 구멍은 찾지 못했다. 고친 것은 없고 감시 기록만 넣었다(`noteLate`): 배율이 멈춘 채 1.5초 넘게 보이는 쪽의 그림(쪽 그림, 필기 그림, 또는 캔버스가 대신 보이는 경우)이 배율과 다르면 무엇이 다르고 무엇이 새 그림을 막고 있는지(쓰는 중인 선, 지우개, 캔버스 사용 중, 만드는 중인 그림, 포기한 그림 등)를 진단 정보의 last steps와 테스트 기록에 "pictures behind the zoom"으로 남기고, 다시 맞으면 몇 초 만인지 남긴다. 사용자 추가 설명: 알람이 뜰 때 생기고, 문서를 닫았다 다시 열어야 풀린다. 0.13.10은 진단 정보의 쪽 보기 부분에 `pictures:` 한 줄을 더한다(마지막으로 그림을 살핀 지 몇 초, 타이머가 도는지, 쓰는 중인 선·지우개·사용 중 캔버스가 남아 있는지, 그림을 포기했는지).

획의 조각이 만나는 자리(0.13.8): 0.13.3부터 획을 조각내 그리는데, 0.13.6의 빌드 서버 사진을 0.13.1과 견주니 완성된 필기 그림은 픽셀 단위로 같았고 "방금 쓴 선"은 화면당 70~125픽셀이 달랐다(255 중 최대 56). 조각은 원으로 끝나고 다음 조각은 같은 원으로 시작하는데, 차례로 칠하면 그 원의 가장자리에서 반쯤 덮이는 픽셀이 두 번 덮여 조금 진해진다. 그림이 선을 넘겨받는 순간 그 픽셀이 변한다. 이제 조각은 이음매(첫 점의 원이 닿는 픽셀과 그 둘레 한 픽셀, 픽셀 경계에 맞춘 네모)만 빼고 칠하고, 이음매는 지운 뒤 그 자리를 지나는 선들을 선마다 한 번에 다시 칠한다(`WetInk.Piece.joint`). 완성된 그림에서 256점씩 나눠 칠하는 긴 획도 같은 식이다: 구간은 양쪽 이음매를 빼고 칠하고, 이음매는 만나는 두 구간을 한 모양으로 한 번 칠한다(`InkPaint.draw`).

글자 선택의 범위를 PDFKit에 맡김(0.13.7, `TextPicker.stretch`): 0.13.6까지는 손가락에 가장 가까운 글자를 앱이 자기 규칙으로 찾고, 처음 누른 단어와 그 글자 사이를 PDF의 글자 순서대로 전부 골랐다. 두 단짜리 쪽과 수식이 있는 쪽에서 그 규칙이 번번이 어긋났는데, 같은 아이패드에서 애플의 기본 PDF 보기는 같은 쪽을 매끄럽게 골랐다(사용자 확인). 그쪽은 범위를 PDFKit이 정한다. 이제 앱도 처음 누른 단어의 가운데와 손가락 위치를 PDFKit에 주고 그 사이를 고르게 한다(`PDFPage.selection(from:to:)`). PDFKit이 아무것도 돌려주지 않을 때만 앱의 규칙을 쓴다. 손가락으로 끄는 동안에는 손가락 아래의 단어를 통째로 잡고, 손잡이를 따로 움직일 때는 글자 단위다. 표시(칠, 손잡이, 메뉴)는 전처럼 앱이 그린다. 선택이 한 번에 60글자 넘게 변하면 테스트 기록에 어느 방식이었는지와 함께 남는다. 실기기 확인 전.

두 단짜리 쪽에서 글자 선택이 옆 단으로 튀던 것(0.13.6): 0.13.5의 테스트 기록에 원인이 그대로 찍혔다. 손가락은 왼쪽 단(가로 238~279)에 있는데 가리킨 것으로 친 글자가 번번이 가로 315, 오른쪽 단의 첫 글자였다. 손가락에 가장 가까운 줄을 고를 때 세로 거리를 가로 거리보다 무조건 앞세웠는데, 두 단의 줄 높이가 어긋난 쪽에서는 손가락이 자기 단의 줄과 줄 사이를 지날 때 옆 단의 줄이 세로로 더 가까웠다. 이제 세로 거리는 가로 거리의 네 배로만 친다: 바로 위아래 줄의 글자가 옆 단의 글자보다 가깝다. 0.13.5에서 짚은 원인(수식의 글자가 번호만 멀리 떨어진 것)은 이 증상의 원인이 아니었다. 그때 넣은 무리 가르기는 해가 없어 남겨 두었다.

수식이 있는 쪽에서 글자 선택 범위가 튀던 것(0.13.5, `TextPicker.letter(near:)`): 0.13.3의 영상에서, 손가락이 분수가 든 줄("Here, the backpropagation path of … is much shorter than")에 있을 때 선택의 시작이 두 줄 위 "attribution map:"으로 튀고 그 사이의 수식 줄이 통째로 딸려 들어갔다(두 번, 같은 자리). 선택은 PDF 안의 글자 순서에서 두 번호 사이의 글자들인데, 수식이 섞인 쪽에서는 화면의 한 줄에 서 있는 글자가 그 순서에서는 멀리 떨어져 있을 수 있다(분수의 일부, 위아래 첨자). 손가락이 그런 글자를 가리킨 것으로 치면 범위가 그 번호까지 한꺼번에 늘어난다. 이제 손가락이 있는 줄의 글자들을 번호가 이어지는 무리로 나누고, 여섯 글자 미만의 무리는 가까이(글자 높이의 3배 이내)에 큰 무리가 있으면 건너뛴다. 단어 사이의 빈칸과 글자보다 훨씬 큰 상자(PDFKit이 빈칸에 주는 자리는 다른 줄까지 걸칠 수 있다)도 손가락이 가리킬 수 있는 글자에서 뺐다. 선택이 한 번에 60글자 넘게 늘거나 줄면 테스트 기록에 어느 글자 때문이었는지 남는다. 그 PDF로 직접 확인하지는 못했고(영상만 봤다), 규칙이 어림이라 다른 모양의 수식에서는 여전히 튈 수 있다.

아주 긴 획이 있을 때 확대를 바꾸면 흐려지고 깜박이던 것(0.13.4): 0.13.3의 테스트 기록에서 밀림은 없어졌지만(5만 2천 점짜리 획에서도 펜을 뗀 순간과 터치가 끝난 순간이 같았다), 필기 그림 한 장이 "drawn whole in 6190.3 ms"였다. 5배에서 만들기 시작한 그림이 9.5배가 된 뒤에 도착해 늘어난 채 보였고, 그 뒤 10초 동안 새 그림이 오지 않았다. 도착하는 순간에는 방금 쓴 선명한 선이 내려가고 흐린 그림이 대신했다. 네 군데를 고쳤다. (1) 굵기가 변하는 긴 획을 256점씩 나눠 칠하고, 그리는 영역에 닿는 구간만 칠한다(전에는 획 전체를 한 모양으로 한 번에 칠했다. 조각이 많은 한 모양은 같은 조각을 나눠 칠하는 것보다 훨씬 오래 걸리고, 확대하면 획의 일부만 그림에 들어가는데도 전부 만들었다). (2) 획 자신의 점이 3픽셀 이내 간격이면 그대로 쓴다(전에는 1.8픽셀을 넘으면 PencilKit 곡선을 다시 계산했다). (3) 확대가 바뀌면 이전 배율로 만들던 그림은 중단시키고 새 배율로 바로 다시 요청한다(`inkAsking`, 그리는 쪽은 구간마다 아직 필요한지 묻는다). (4) 지금 배율이 아닌 그림이 도착하면 방금 쓴 선은 내리지 않고, 지금 배율의 그림이 올 때까지 둔다.

확대해서 펜슬을 아주 빠르게 움직일 때 밀리던 것(0.13.3): 실기기의 테스트 기록에서, 7배 확대로 쓴 한 획이 24,056점이었고 펜을 뗀 뒤 앱이 8초 뒤처져 있었다("3초·4초 응답 없음"도 같은 구간). 세 군데를 고쳤다. (1) 쓰는 중인 획 전체가 위쪽 타일에 있어서, 펜이 움직일 때마다 그 자리를 지나는 획의 모든 조각을 다시 그렸다. 좁은 곳을 왕복하면 획이 길어질수록 느려졌다. 이제 확정된 조각은 확정되는 순간 아래쪽 타일(자기 비트맵에 덧그리는 타일)에 한 번 그리고, 위쪽 타일에는 아직 바뀌는 끝부분만 둔다. (2) 만년필은 펜을 뗄 때 끝을 뾰족하게 다듬는데, 그때 획 전체를 처음부터 다시 만들었다. 이제 다듬어서 바뀐 점부터만 다시 만든다(`PenLine.reshapedFrom`, `WetInk.restart(from:)`). (3) 선의 모양을 만들 때 점마다 원(확대하면 40각형)을 넣었는데, 원의 거의 전부가 앞뒤 띠에 덮여 있었다. 이제 원은 선의 끝, 파선의 끝, 크게 꺾이는 곳에만 넣고 나머지는 두 띠 사이의 틈만 작은 삼각형으로 메운다(직선 변과 원호의 차이가 0.03픽셀 미만일 때만. `InkPaint.shape`). 쓰는 중과 쓴 뒤의 그림이 같은 코드를 쓰므로 둘 다 가벼워진다. 실기기에서 얼마나 나아졌는지는 테스트 기록으로 확인해야 한다.

빌드와 검증을 나눔(0.13.2): 올리면 앱을 빌드해 IPA만 만든다(몇 분). 시뮬레이터에서 사진 102장을 찍고 터치 시험을 하던 한 시간은 매번 돌지 않고, Actions > iPad build > Run workflow에서 "verify"를 켰을 때만 돈다. 앱은 쓰는 사람이 아이패드에서 직접 써 보고, 아이패드의 화면 기록으로 찍은 영상과 앱의 테스트 기록을 넘겨준다. 테스트 기록(`TestRecorder`, 설정 > 진단 > 테스트 기록 시작): 켜면 화면 맨 위에 "기록 중" 표시가 뜨고, 그때부터 앱이 한 일을 [표시가 뜬 뒤 초, 시각]과 함께 적는다(도구 바꿈, 펜슬 제스처, 터치가 닿고 떨어진 때, 펜·지우개의 시작과 끝, 직선·도형으로 바뀐 때, 필기 그림이 넘겨받은 때, 디버그 빌드에서만 남던 앱의 기록 전부). 표시를 누르면 끝나고 글 파일 하나를 공유 시트로 내보낸다. 영상에 표시가 나타나는 순간이 기록의 0초다. 기록은 켰을 때만 쌓이고 아이패드 밖으로 앱이 보내지 않으며, 문서 내용은 들어가지 않는다. 이 방식에서는 빌드 서버가 컴파일만 확인하므로, 계산이 맞는지 보던 자체 점검도 "verify"를 켠 빌드에서만 돈다.

쉬지 않고 겹쳐 그을 때 펜을 떼는 순간이 느려지던 것(0.13.1, `WetInk.show`): 0.12.3은 펜이 움직이는 동안의 비용만 줄였다. 0.13.0의 빌드 서버 측정(3배 확대, 화면 폭의 물결선을 쉬지 않고 겹쳐 씀)에서 펜을 뗄 때 걸린 시간이 대기 중인 선이 5개일 때 0.58초, 10개일 때 1.0초, 15개일 때 1.7초로 선 수에 비례해 늘었다. 대기 중인 선의 타일이 스스로 그리는 레이어였기 때문이다: 그런 레이어는 다시 그릴 영역을 먼저 지우므로, 선 하나가 끝날 때마다 그 자리를 지나는 대기 중인 선을 전부 다시 그렸다. 이제 대기 타일은 자기 비트맵을 갖고, 끝난 선은 이미 그려진 것 위에 그 선만 덧그린다(순서대로 덧그리므로 한 번에 전부 그린 것과 픽셀이 같다). 선이 내려갈 때(그림이 넘겨받거나 지우개·실행 취소)만 해당 부분을 처음부터 다시 그리는데, 보통은 그림이 대기 중인 선을 모두 넘겨받아 타일째로 치운다. 타일 하나에 메모리가 0.6MB쯤 더 든다(대기 중인 선이 있는 곳에만, 그림이 넘겨받으면 반납). 캔버스를 미루는 것(`-demoEagerCanvas`)은 같은 측정에서 차이가 없었다: 시뮬레이터에서는 그 비용이 드러나지 않았고, 실기기 진단에 있던 3초 멈춤이 그것 때문인지는 확인되지 않았다.

긋자마자 꽉 쥐기로 지우개를 들면 안 지워지던 것(0.13.1, `rubByWatch`): 0.13.0의 화면 녹화에서 확인했다. 획을 쓰고 펜슬을 꽉 쥐어 지우개로 바꾼 뒤 바로 문지르면, 도구는 지우개이고 지우개 원이 획 위를 2초 넘게 따라다니는데 획이 남는다. 지우개의 드래그 인식기는 지우개가 손에 있을 때 닿은 터치만 받는다. 꽉 쥐기는 쥔 손을 놓을 때 도구를 바꾸는데, 한 동작으로 쥐고 바로 대면 펜 끝이 그보다 먼저 닿는다. 그 터치는 펜 아래에서 시작했고, 펜은 도구가 바뀌면 쓰던 선을 버리며, 그 뒤로 그 터치를 받는 것이 없었다. 원은 모든 터치를 보는 감시 인식기가 그리기 때문에 따라다니기만 했다. 이제 지우개가 손에 있는데 드래그 인식기가 잡지 못한 펜슬 터치가 쪽 위에서 움직이면, 감시 인식기가 본 길을 따라 지우개가 그대로 지운다(되돌리기 한 번으로 묶이는 것도 같다). 손가락 터치는 이 길로 지우지 않는다(스크롤과 구별할 수 없어서). 실기기에서 고쳐졌는지는 확인 전이다.

지우개를 들자마자 펜으로 되돌아가던 것(0.13.1): 0.13.0의 실기기 진단 정보에 도구가 같은 초 안에 "지우개 → 펜"으로 바뀐 기록이 두 번 있었고, 지우개가 빗나갔다는 기록은 없었다. 지우개가 종이에 닿기 전에 내려진 것이다. 그럴 수 있는 길 두 가지를 막았다. (1) PencilKit 캔버스가 "도구 사용이 끝났다"고 알리면 손에 든 도구가 무엇이든 "사용했다"로 쳤다. 캔버스에는 앱이 필기를 코드로 넘겨주는데(마지막 획 직후일 때가 많다), 그때 그런 알림이 오면 "지우고 나면 이전 도구로 돌아가기"가 켜진 지우개는 쓰기도 전에 내려진다. 이제 손에 든 도구가 캔버스에서 일하는 도구이고 실제로 캔버스에 터치가 있었을 때만 친다. (2) 펜슬 두 번 탭과 꽉 쥐기가 0.45초 안에 잇달아 오면(펜슬 프로를 세게 쥔 채 탭하면 둘 다 온다) 지우개를 들었다가 바로 내려놓게 된다. 이제 그 안에 온 두 번째는 받지 않는다. 어느 쪽이었는지는 확인하지 못했다. 진단 정보의 "last steps"에 펜슬 제스처, 도구가 사용 후 내려진 것, 캔버스의 알림을 받지 않은 것이 남고(8개에서 16개로 늘림), 지우개 종류와 자동 내려놓기 설정도 함께 적힌다.

긋자마자 지우개로 지우면 안 지워지던 것(0.13.1): 지우개는 "지난번에 들은 위치에서 지금 위치까지"의 직선이 획에 닿는지를 본다. 앱이 잠깐 바쁘면 그 사이 터치가 지나간 자리들이 한꺼번에 들어오고 지우개는 마지막 위치만 들었다. 획 위를 문질러도 바쁘기 전 위치와 바쁜 뒤 위치를 잇는 직선이 획을 비켜 가면 아무것도 지우지 못했다. 이제 드래그 인식기가 터치가 지나간 자리를 모두 모아 두고(`ShapeGesture.takeTrail`, 묶여 들어온 것 포함) 지우개가 그 길을 따라 판정한다. 앱이 바빴던 까닭도 줄였다: 0.12.3은 마지막 획에서 1초 뒤에 숨은 캔버스에 필기를 넘겼는데(PencilKit이 메인 스레드에서 다시 그린다), 펜을 지우개로 바꿔 들고 돌아오는 때와 겹쳤다. 이제 3초 쉬었고 펜슬이 쪽 위에 떠 있지 않을 때만 넘긴다. 지우개가 아무것도 못 만났을 때 진단 정보에 드래그가 몇 번에 걸쳐 몇 자리로 들어왔는지, 가장 길게 기다린 시간이 얼마인지가 남는다. 이 원인은 코드에서 찾은 것이고 실기기에서 재현해 확인하지는 못했다. 부분 지우개(PencilKit의 것)는 이 경로를 쓰지 않는다.

획이 깜박이던 것(0.12.3에서 생김, 0.13.0에서 고침): 0.12.3은 쓰는 중인 선의 타일과 대기 중인 선의 타일을 각각 뷰에 딸리지 않은 레이어에 담았다. 그런 레이어는 하위 레이어가 들고 나는 것을 0.25초 페이드로 보여 준다(뷰의 레이어는 그러지 않는다). 펜을 떼면 선이 쓰는 쪽 타일에서 바로 지워지고 대기 쪽 타일에는 서서히 나타나서, 획마다 한 번 깜박였다. 두 묶음을 뷰에 담아 고쳤다(`WetInk.waitingHost`, `liveHost`). 빌드 서버의 사진은 몇 초 뒤의 정지 화면이라 이런 움직임은 잡지 못한다. 실기기에서 본 것으로 알게 됐다.

긋고 멈추면 직선(0.12.3, `PenShapes.swift`): 펜이나 형광펜으로 선을 긋고 끝에서 펜을 떼지 않은 채 0.45초 멈추면 그 선이 직선으로 펴진다. 멈춤은 화면 기준으로 판정한다(3.5포인트 안에 머무름: 확대해도 손이 느끼는 기준이 같다). 펴는 것은 손으로 그은 직선일 때만이다: 화면에서 20포인트 이상이고, 양 끝을 잇는 길에서 길이의 1/16 넘게 벗어나지 않으며, 그 길보다 1.25배 넘게 길지 않은 선. 글자를 쓰다 멈춘 것은 펴지 않는다. 편 뒤 펜을 계속 대고 움직이면 시작점은 그대로이고 끝이 펜을 따라가며, 수평·수직·45도에서 5도 안으로 들어오면 그 방향에 붙는다. 굵기는 그 선의 평균 굵기이고, 만년필이면 양 끝의 뾰족함은 남는다. 펜을 떼면 획 하나로 저장된다(실행 취소 한 번에 통째로 사라진다). Apple Pencil Pro에서는 펴질 때와 방향에 붙을 때 손에 진동이 온다(`UICanvasFeedbackGenerator`). 펜·형광펜 설정의 "긋고 멈추면 직선으로 펴기"로 끈다.
긋고 멈추면 도형(0.12.3, `ShapeFinder`): 펜으로 그린 선이 시작한 자리 근처로 돌아와 있으면(양 끝 사이가 선 길이의 15% 이내) 멈췄을 때 도형으로 본다. 그린 길을 같은 간격의 72점으로 다시 잡고 두 가지를 맞춰 본다. 둥근 쪽은 점들이 퍼진 방향으로 기울기를 정하고 장·단축 길이를 점들에 직접 맞춘다(최소제곱). 각진 쪽은 선이 꺾이는 자리(모서리)를 찾아 3~5개면 그 다각형과 점들 사이의 평균 거리를 잰다. 더 잘 맞는 쪽을 고르고, 어느 쪽도 맞지 않으면(다각형은 평균 거리가 크기의 9%, 타원은 13% 초과) 그린 그대로 둔다. 네 모서리가 모두 직각에서 14도 안이면 직사각형으로 반듯하게 하고, 8도 안으로 누워 있으면 수평·수직에 맞춘다. 타원은 단축이 장축의 88% 이상이면 원으로 하고, 8도 안으로 누워 있으면 수평·수직에 맞춘다. 화면에서 24포인트보다 작은 것은 바꾸지 않는다(글자 ㅇ, ㅁ). 도형이 된 뒤에는 펜을 움직여도 그대로이고, 펜을 떼면 도형 도구로 그린 것과 같은 획 하나로 저장된다(펜 굵기, 필압 없음). 모서리가 여섯 개 이상인 도형은 떨리는 손으로 그린 원과 구별이 안 되어 원이나 타원이 된다. 형광펜은 직선으로만 편다.

끝점 붙기(0.12.3): 직선으로 편 선의 시작이나 끝이 그 쪽에 있는 다른 직선(화면에서 20포인트 이상, 최근 400획 안)의 끝에서 화면 기준 12포인트 안이면 그 끝에 놓인다. 방향에 붙는 것보다 먼저다. 붙을 때도 Apple Pencil Pro에 진동이 온다. 도형의 모서리나 선의 중간에는 붙지 않는다.

셈 점검(`SelfCheck.swift`): 화면 없이 확인할 수 있는 계산(멈춤 판정, 직선 판정, 방향에 붙기, 필압 곡선과 보정, 획 안정화, 도형 인식, 끝점 붙기, 파선·점선의 위치, 붓의 굵기)은 `-selfCheck`로 실행하면 앱 기록에 "check: … ok/FAILED"로 남고, 빌드 서버는 FAILED가 하나라도 있으면 빌드를 실패로 처리한다. 프로젝트에 단위 테스트 타깃이 없어서 그 자리를 대신한다. 도형 인식 점검은 흔들리게 그린 직사각형(끝이 8% 덜 닫힘), 30도 돌린 직사각형, 삼각형, 오각형, 원(4% 겹침), 30도 돌린 타원, 5도 누운 타원이 각각 그 도형으로, 크기·기울기 오차 몇 % 안에서 잡히는지와 물결선·별·덜 닫힌 고리가 도형이 되지 않는지를 본다. 화면까지 이어진 동작은 `-demoHeldShapes`가 같은 도형들을 펜이 쓰는 경로로 넣고 멈춘 뒤 찍은 사진(`59-held-shapes`)과 기록으로 확인하며, 네 도형 중 하나라도 안 잡히거나 끝점이 안 붙으면 빌드가 실패한다.

형광펜 항상 직선(0.13.0): 형광펜 설정의 "항상 직선으로 긋기"를 켜면 형광펜이 닿은 자리에서 펜이 있는 곳까지 늘 직선으로 그어진다. 수평·수직·45도에서 5도 안이면 그 방향에 붙는다(글줄을 따라 그을 때 반듯해진다). 기본은 꺼짐.

붓(0.13.0): 펜 종류에 붓을 더했다. 필압 곡선이 따로다(`PressureCurve.brush`: 힘이 없으면 굵기의 0.1배, 펜슬 최대 힘의 72%에서 2.8배, 그 사이는 거의 고르게). 획의 처음과 끝은 늘 뾰족하고(펜끝 선명도 90% 고정), 속도 반응은 50% 고정이다. 필압 감도 슬라이더는 붓에서 50~100% 범위로 쓰인다(필압에 반응하지 않는 붓은 붓이 아니어서). 손가락처럼 힘을 알리지 않는 입력에서는 굵기가 일정하고 끝만 뾰족하다. 볼펜(필압 없음)·만년필·펜·연필은 전과 같다.

점선·파선(0.13.0, `DashPattern`): 펜 설정의 "선 모양"에서 실선·파선·점선을 고른다. 무늬는 선을 따라 잰 길이로 놓는다. 파선은 굵기의 3배를 긋고 3배를 비우며(끝이 둥글어서 보이기는 4배 긋고 2배 비움), 점선은 굵기의 2.25배마다 점 하나다. 길이가 쪽 기준이라 확대하면 선 굵기와 같은 비율로 커지고, 필압으로 굵기가 변해도 간격은 설정 굵기를 따른다. 파선 하나는 획 하나다: 지우개가 통째로 지우고, 올가미가 통째로 잡고, 실행 취소 한 번에 사라진다. 틈은 폭이 0인 점으로 표시한다. 쓰는 동안과 쓴 뒤 모두 같은 코드가 틈을 건너뛰고 그리므로(`InkPaint.shape`) 펜을 뗄 때 모양이 바뀌지 않는다. PencilKit에 넘기는 획에서는 틈의 양 끝에 "PencilKit이 아무것도 그리지 않는 크기(2)에 불투명도 0"인 점을 두 개씩 둔다(PencilKit은 점들 사이를 매끄러운 곡선으로 잇기 때문에 하나만 두면 틈으로 굵기가 조금 새어 나온다). 내보낸 PDF와 AI에게 보내는 그림의 필기는 PencilKit이 그리므로, 빌드 서버는 PencilKit이 그 획을 실제로 몇 토막으로 그리는지도 재서 기록한다. 긋고 멈춰서 편 직선과 도형, 도형 도구로 그린 도형도 펜의 선 모양을 따른다. 형광펜과 연필은 늘 실선이다.

필압(0.12.3, `AppPen.swift`): 힘을 펜슬이 알릴 수 있는 최대 힘에 대한 비율(0~1)로 바꿔 쓴다(`maximumPossibleForce`). 굵기 곡선은 펜 종류마다 따로 둔다(`PressureCurve`: 힘이 없을 때와 가장 셀 때의 굵기 배율, 그 사이의 굽은 정도). 만년필의 곡선은 전과 같은 값이 나오도록 옮겼다(점검으로 확인). 힘은 굵기에 쓰기 전에 고르게 한다: 펜이 막 닿은 처음 0.04초는 값이 가장 튀므로 더 세게(시간 상수 30ms), 그 뒤로는 약하게(6ms). 애플 펜슬은 힘을 우선 추정값으로 알리고 곧 참값으로 고쳐 알리는데(`touchesEstimatedPropertiesUpdated`), 그 고친 값을 받아 해당 지점부터 굵기를 다시 셈한다(`PenLine.correct`). 다시 그리는 것은 아직 확정되지 않은 구간뿐이고, 이미 확정된 구간에 늦게 온 값은 선을 바꾸지 않는다. 보통 속도로 쓰는 획에서는 고친 값이 확정 뒤에 오는 일이 많아서, 실제로 달라지는 것은 주로 펜이 막 닿아 거의 움직이지 않은 획의 시작이다.

획 안정화(0.12.3): 안정화는 선이 펜을 조금 늦게 따라가게 해서 손떨림을 펴는데, 전에는 그 늦는 정도가 속도와 무관하게 같았다. 이제 펜이 느릴수록 더 펴고(화면에서 초당 0에 가까우면 전의 1.6배), 빠를수록 덜 늦는다(초당 180포인트에서 전과 같고, 600포인트에서 절반, 1500포인트에서 4분의 1쯤). 손이 떨리는 것은 천천히 쓸 때이고, 빨리 긋는 선은 어디론가 가는 중이라 바짝 따라가는 편이 낫기 때문이다(1€ 필터와 같은 생각). 설정값("획 안정화" %)의 뜻은 그대로다. 점검: 초당 80포인트로 가며 12Hz로 떨리는 선은 전보다 덜 흔들리고, 초당 1500포인트의 선은 펜에 절반 이하로 뒤처진다.

쪽 고르기와 합치기(0.9.0, `PDFCopy`): 고른 쪽의 객체를 원래 파일에 적힌 그대로(글꼴, 그림, 압축된 스트림까지) 새 파일로 옮겨 적는다. 다른 쪽은 새 파일에 들어가지 않고, 옮긴 쪽의 글자는 원본과 같다. 쪽에서 다른 쪽을 가리키는 링크는 그 쪽이 함께 옮겨질 때만 남는다. 합치기는 문서마다 내보내기와 같은 사본(필기를 그려 넣은 것)을 만든 뒤 그 쪽들을 한 파일로 옮긴다. 암호화된 PDF는 이렇게 읽을 수 없어서 PDFKit이 쪽을 새로 써서 만든다(이 경우 일부 글꼴의 글자 정보가 깨질 수 있다).

스레드: PDFKit의 문서와 쪽 객체는 여러 스레드에서 함께 쓰라고 만든 것이 아니다. 0.6.0은 화면에 떠 있는 문서의 쪽을 그리기 큐와 쪽 이동 창의 그림 작업에서도 썼다. 0.7.0부터 그리기 큐와 쪽 이동 창은 같은 파일을 따로 연 자기 사본만 쓴다(`PictureSource`, `ThumbnailSource`).

메모리: 메모리 부족 경고를 받으면 안 보이는 쪽의 그림을 버리고, 그 문서를 닫을 때까지 그림의 화소 한도를 절반으로, 캔버스의 배율 상한을 3배에서 1.5배로 낮춘다.

진단(설정 → 진단): 빌드 서버에서는 실기기에서 생기는 일을 볼 수 없어서, 앱이 화면에 떠 있다가 끝난 실행의 수, 메모리 부족 경고의 수, 시스템(MetricKit)이 알려 주는 충돌·멈춤·종료 사유, 그리고 마지막으로 보던 쪽의 레이어별 해상도를 아이패드 안에 적어 둔다. "진단 정보 복사"로 글로 꺼낼 수 있고, 앱이 어디로 보내지는 않는다.

쪽을 한 번 더 그리기: 쪽이 화면에 가까이 오면 앱이 그 쪽을 화면 해상도 그대로 메인 스레드 밖에서 그려 PDFKit의 그림 위에 덮는다(`PagePicture`, 쪽 오버레이의 맨 아래 층). 한 쪽이 900만 화소를 넘게 되는 배율에서는 보이는 부분과 그 둘레만 그리고, 스크롤해서 그 밖으로 나가면 다시 그린다. 그림이 준비되기 전과 그림이 닿지 않는 곳에는 PDFKit의 그림이 보인다. 화면에서 한 화면 반 넘게 벗어난 쪽의 그림과 메모리가 모자랄 때 안 보이는 쪽의 그림은 버린다. 문서 안 검색에서 찾은 낱말의 노란 표시는 PDFKit의 것이 이 그림에 가려지므로 오버레이에 직접 그린다. 0.8.0부터는 늘 켜져 있고 설정이 없다.

이 층은 "실기기에서 문서가 다른 필기 앱보다 낮은 해상도로 보인다"는 보고 때문에 넣었는데, 빌드 서버의 시뮬레이터에서는 그 현상이 나오지 않았다. 글자 PDF(맞춤 배율, 2.5배, PDFKit이 허용하는 최대 배율), 화면보다 훨씬 큰 쪽, 쪽 전체가 스캔 그림인 문서(밝은 종이와 어두운 종이)를 이 층을 켠 화면과 끈 화면으로 찍어 비교하면 글자 PDF는 회색 단계 하나 안쪽으로 같고, 스캔본은 그림을 줄이고 늘리는 방식이 조금 다를 뿐 눈으로 구별되지 않는다. 그러니 이 층이 실기기에서 무엇을 바꾸는지는 아이패드에서 켜고 끄며 봐야 안다. 쪽이 미리 그려져 있다는 점은 시뮬레이터의 정지 화면으로는 잴 수 없다.

지우개: 획 지우개는 앱의 것이고(0.8.0) 부분 지우개는 PencilKit의 것이다. 둘 다 크기가 있고(화면 포인트 6~60, 도구 막대에 세 가지), 쪽에 보이는 원이 지우는 범위다: 획 지우개는 원에 닿은 획을 통째로 지우고, 부분 지우개는 원이 지나간 자리만 지운다. 획 지우개는 지우개가 내려올 때 쪽의 획과 각 획이 차지하는 자리를 한 번 적어 두고, 움직이는 동안에는 그 자리에 들어간 획만 살핀다. "형광펜만 지우기"는 같은 지우개가 형광펜 획만 고르는 것이다. 한 번 문지른 것이 실행 취소 한 단계다. AI 펜 표시는 아무 터치도 가로채지 않는 제스처 인식기(`TouchWatcher`)가 지우개의 자리를 따라가며 지난 곳을 찾는다. 원은 지우는 동안, 그리고 애플 펜슬을 화면 위에 띄우고 있는 동안 보인다. PencilKit의 부분 지우개는 굵기 값만큼의 화면 포인트를 지운다(빌드 서버에서 화면 맞춤 배율로 잰 값: 굵기 40은 40포인트, 16은 16포인트; 확대한 상태에서는 재지 못했다).

확대와 이동(0.8.0): 축소는 한 쪽이 통째로 보이는 데서 조금 더까지만 된다. 확대는 화면 너비 맞춤의 6배까지다(PDFKit의 기본 한도인 쪽 크기의 5배는 큰 아이패드에서 화면 맞춤의 2.2배밖에 안 됐다). PDFKit의 스크롤 뷰는 드래그를 시작한 방향(가로 또는 세로)으로만 움직이게 잠겨 있어서 그 잠금을 풀었다: 확대한 쪽이 손가락이 가는 대로 비스듬히도 움직인다.

충돌과 멈춤(0.7.1의 진단 기록): 받은 기록 세 건은 모두 메인 스레드가 화면을 그리는 SwiftUI 내부에서 멈추거나 죽은 것이었다. 진단 코드가 시스템의 충돌 보고를 받는 스레드에서 설정 저장소(UserDefaults)에 횟수를 쓰고 있었고, 화면들이 그 저장소를 지켜보고 있어서 두 스레드가 화면 상태를 동시에 건드릴 수 있었다(세 건 중 두 건이 보고를 받은 실행에서 몇 분 안에 일어났다). 0.8.0은 저장소를 메인 스레드에서만 쓰고, 슬라이더를 끄는 동안 값이 바뀔 때마다 저장하던 것을 멈춘 뒤 한 번 저장하게 했다. 첫 번째 멈춤은 이것으로 설명되지 않아 원인이 확인된 것은 아니다. 그래서 진단을 보강했다: 메인 스레드가 3초 넘게 대답하지 않으면 그때 앱이 하던 일(마지막 몇 단계)을 기록하고, 충돌 보고의 호출 스택을 끝까지(앱 자신의 코드가 나오는 데까지) 적으며, 빌드마다 기호 파일(dSYM)을 남겨 그 위치를 이름으로 찾을 수 있게 했다. AI 펜을 든 동안 실행 취소 기록을 꺼 두던 코드도 없앴다(AI 펜이 캔버스에 쓰지 않게 되어 필요가 없어졌고, 껐다 켜는 짝이 어긋나면 예외가 나는 코드였다).

충돌(0.8.0의 진단 기록): 0.8.0에서도 같은 자리의 충돌이 세 번 이어졌다(설치 직후 1분 안에 세 번 실행, 세 번 모두 SwiftUI의 화면 갱신 안에서 SIGSEGV; 그 뒤로는 잘 돌았다). 호출 스택을 끝까지 적게 한 덕에 메인 스레드라는 것, 화면 배치 → SwiftUI 갱신 → AttributeGraph 순서라는 것은 알았지만 시스템 코드의 이름은 알 수 없고 앱 자신의 코드는 맨 바깥(main)뿐이라 원인은 여전히 확정하지 못했다. 0.9.0은 세 가지를 바꿨다. 실행 중의 단계를 그때그때 파일에 적어 두고 다음 실행이 읽는다(충돌한 실행이 무엇을 하다가 몇 초 만에 끝났는지가 진단 정보에 남는다). 서재의 격자를 화면에 들어올 때 카드를 만드는 시스템 격자(LazyVGrid)에서 모든 카드를 한 번에 놓는 자체 배치(`ShelfGrid`)로 바꿨다(스택의 모양이 목록의 자식을 넣고 빼는 자리와 닮았고, 실행 직후 화면 크기가 정해지는 동안 일어난 것으로 보여서다). 문서를 열 때 "최근에 연 순서"를 바로 바꾸지 않고 화면이 자리 잡은 뒤에 바꾼다(문서를 여는 전환 도중에 서재 목록의 순서가 바뀌지 않게). 이 셋은 추정에 따른 방어이고, 원인을 고쳤다고 확인된 것은 아니다.

쓰고 나면 이전 도구로: 지우개·형광펜·도형마다 설정에 스위치가 있다. 켜 두면 한 번 쓰고 펜을 떼는 순간 그 전에 들고 있던 도구로 돌아간다.

저장과 속도: 필기는 바뀔 때마다 바로 쓰지 않고 0.8초 뒤에 메인 스레드 밖에서 쓴다(앱을 떠날 때, 문서를 닫을 때, 내보내기와 쪽 추가 전에는 기다리지 않고 바로 쓴다). PDF 가져오기의 파일 복사, 서재의 표지 그리기, 쪽 이동 창의 쪽 그림도 메인 스레드 밖에서 하고, 표지는 한 번 그려 문서 옆에 `cover.jpg`로 둔다.

도형은 끄는 동안 미리보기 선으로 보이다가 손을 떼면 굵기가 일정한 PencilKit 획이 된다. 그래서 지우개·올가미·실행 취소가 그대로 통한다.

어두운 종이는 쪽을 그릴 때 흰 바탕에 쪽을 그린 뒤 밝기를 뒤집고(차이 혼합), 쪽을 한 번 더 그려 색상만 되돌린다(색상 혼합). 필기는 PencilKit이 어두운 화면용 색으로 보여 준다. 내보내기와 Claude에게 가는 그림은 따로 연 문서로 만들어 늘 원래 색이다.

가져온 PDF는 다시 쓰지 않는다. PDFKit으로 문서를 저장하면(`PDFDocument.write`) 모든 쪽을 새로 그려 넣은 파일이 만들어지는데, 그 파일에서는 한글 글꼴처럼 일부만 넣은 글꼴의 글자 정보가 깨져서 글자를 뽑으면 엉뚱한 글자가 나온다. 0.4.0까지는 "쪽 추가"가 이 방식이어서, 쪽을 추가한 문서는 Claude에게 가는 본문과 문서 안 검색이 깨졌다. 지금은 추가한 쪽을 PDF 옆의 `pages.json`에 적어 두고 문서를 열 때마다 끼워 넣는다(`DocFile.open`). 0.4.0 이하에서 쪽을 추가했던 문서는 파일이 이미 바뀌어 있으니, 글자가 필요하면 원본을 다시 가져와야 한다.

노트 종이는 줄이 그려진 실제 PDF 쪽이다. 무늬는 한 번 계산해서 화면용 쪽에도, 내보내기에도 같은 것을 쓴다.

내보내기는 원본 파일을 그대로 두고 그 뒤에 바뀐 부분만 덧붙인다(PDF의 증분 갱신, `PDFAppend`). 필기·수식·표시는 쪽마다 그림 한 장(쪽의 3배 해상도, 쓴 곳만 잘라서)으로 쪽 내용 끝에 얹히고, 추가한 쪽은 새 쪽으로 들어간다. 원본의 바이트가 그대로라 글자 선택·검색·복사가 원본과 같다. 암호화됐거나 구조가 어긋난 파일은 덧붙일 수 없어서 PDFKit으로 새로 써서 내보내며, 이때는 보이는 모습은 같아도 글자 정보가 달라질 수 있다. 암호 없이 열리지만 인쇄·복사 등이 제한된 PDF는 PDFKit이 그대로 쓰면 어떤 암호로도 열리지 않는 파일이 나오므로, 원본과 같은 권한으로 다시 잠가서 쓴다(여는 데 암호는 필요 없고 제한은 유지). 써 놓은 파일이 열리지 않으면 내보내기를 실패로 처리한다. 덧붙이는 방식은 먼저 파이썬 기준 구현으로 실제 PDF 370여 개(표 형식·스트림 형식 교차 참조, 객체 스트림, 선형화, 여러 번 갱신된 파일 포함)에 돌려 봤고, 암호가 걸린 2개와 손상된 1개를 뺀 전부가 통과했다. 앱의 Swift 코드는 그 구현을 그대로 옮긴 것이고, 빌드 서버에서 네 가지 문서(쪽을 추가한 샘플, 돌려지고 잘린 쪽이 있는 문서, 객체 스트림을 쓰는 문서, 쪽을 추가한 줄 노트)를 내보내 쪽 그림과 글자를 확인한다.

## 직접 확인하지 못한 것

0.8.0에서 빌드 서버로 확인한 것: 손가락으로 쓴 선이 쓴 직후(앱이 도형으로 보여 주는 동안)와 2초 뒤(필기 그림에 들어간 뒤)에 같은 픽셀로 그려지는지(천천히 쓴 두 선은 가장자리 픽셀 값까지 같았고, 빠르게 쓴 선은 0.4픽셀쯤 옮겨질 뿐 가장자리 폭은 같았다; 화면 픽셀에 맞추기 전에는 선마다 양쪽으로 반 픽셀씩 번졌다), 쪽 글자의 가장자리(글자 블록에서 중간 밝기 픽셀의 비율이 PDFKit만일 때 0.92, 맞추기 전 0.87, 맞춘 뒤 0.54), 글자 위에 그은 형광펜 아래에서 글자가 그대로 검은지와 겹친 자리가 한 번 그은 자리와 같은 색인지, 크기 48과 8의 획 지우개와 실행 취소, 확대한 채 비스듬히 끌었을 때 가로·세로로 함께 움직이는지, 축소와 확대의 한계, A5 가로와 A3 노트, 연필(PencilKit)로 쓰기. 확인하지 못한 것: 애플 펜슬로 쓸 때의 지연과 필압, 아이패드(iPadOS 27)에서의 선명도와 메모리, 충돌이 실제로 없어졌는지(원인으로 지목한 것은 시뮬레이터에서 재현되지 않았다), 파일 앱 공유 시트에 앱이 보이는지, 필기가 아주 많은 쪽에서 그림을 처음 그리는 시간(시뮬레이터에서는 PencilKit이 그려야 하는 예전 획이 있는 쪽이 0.3~1초 걸렸다. 그동안은 캔버스가 보인다).

빌드 서버의 시뮬레이터에서 가짜 서버로 확인한 것까지가 검증 범위다. 0.6.0부터는 시뮬레이터에서 손가락 터치를 실제로 넣는 테스트(`AIPencilUITests`, `uitests.yml`)가 있어서, 손가락 필기로 AI 펜 표시 만들기, 지우개로 표시 지우기와 실행 취소, 펜과 형광펜 긋기, 형광펜만 지우기, 지운 뒤 이전 도구로 돌아가기, 도형 끌어 그리기를 빌드 때마다 해 본다. 애플 펜슬은 시뮬레이터에 없어서 펜슬로 하는 같은 동작은 확인하지 못했다. 0.7.0의 앱 자체 펜은 손가락 터치로 세 줄을 잇달아 쓰고, 실행 취소하고, PencilKit 펜으로 쓴 직후와 손을 멈춘 뒤의 화면을 찍는 것까지 이 테스트에 들어 있다. 0.7.1부터는 최대 배율로 확대한 채로 쓰기(PencilKit 펜과 앱 자체 펜), 손가락으로 스크롤하기, 지우기도 한다: 선은 손가락이 지나간 자리에 그려지고, 캔버스 타일은 점당 10픽셀(5배 × 2)로 만들어진다. 앱 자체 펜이 손을 따라오는 지연, 필압 감도와 획 안정화의 실제 느낌, 확대한 채 빠르게 스크롤할 때 캔버스가 따라오는 모습, 애플 펜슬을 띄웠을 때 지우개 원이 보이는지는 아이패드에서만 알 수 있다. 실제 Claude API 호출(웹 검색 포함), 실제 애플 펜슬로 그은 획과 필압, 펜슬 두 번 탭·꽉 쥐기, 손가락으로 표시를 눌러 여는 동작, 실기기의 키체인 저장은 아이패드에서 직접 해 봐야 안다.

내보내기는 시뮬레이터에서 만든 파일을 맥의 PDFKit, pypdf, pdf.js 세 가지로 열어 쪽 수·글자·그림을 확인했다. 내보낸 뒤 뜨는 공유 창, 수백 쪽짜리 문서를 내보낼 때 걸리는 시간과 메모리, 다른 앱(굿노트, 어도비 등)에서 열었을 때의 모습은 확인하지 못했다. 암호화된 PDF의 내보내기는 열리고 모습도 맞지만 글자 정보는 깨진다(위에 적은 PDFKit의 한계).
