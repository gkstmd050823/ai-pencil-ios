# AI 펜슬 (아이패드)

PDF에 애플 펜슬로 필기하다가 모르는 부분에 동그라미를 치면 그 부분을 설명해 주는 앱의 아이패드판. 안드로이드판을 Swift, PencilKit, PDFKit으로 다시 만드는 중이다.

지금 들어 있는 것:

- 서재: PDF 가져오기, 종이를 골라 새 노트 만들기(백지·줄·모눈·점·코넬), 폴더, 정렬, 문서 찾기, 이름 바꾸기
- 필기: 만년필·펜·볼펜·연필(굵기는 밀리미터 단위로 0.1~2.0, 도구 막대에 굵기 세 칸; 필압 감도와 획 안정화; 색 18가지와 직접 고르기), 글자를 가리지 않는 형광펜, 지우개(획/부분, 둘 다 크기 조절, 형광펜만 지우기, AI 펜 표시 지우기, 이 쪽 필기 모두 지우기), 도형(직선·화살표·네모·동그라미), 올가미, 실행 취소, 한 번 쓰고 나면 이전 도구로 돌아가기(지우개·형광펜·도형), 애플 펜슬 두 번 탭과 꽉 쥐기
- 문서 탭(연 문서가 쪽 위에 탭으로 남고, 눌러서 오가고, ×로 닫는다), 읽기 전용 모드(눈 모양 단추: 손가락은 넘기기만, 펜은 AI 펜만), 쪽을 골라 PDF로 내보내기("1-3, 7"), 문서 합치기(서재에서 문서를 길게 눌러 "다른 문서와 합치기")
- 서재: 문서를 여러 개 또는 전부 골라 한꺼번에 옮기기·합치기·삭제(오른쪽 위 체크 단추), 문서를 끌어서 폴더에 넣기(폴더 안에서는 "폴더 밖으로" 칸에 놓기)
- 문서: 쪽 이동, 목차, 책갈피, 문서 안 검색, 한 쪽씩/두 쪽씩/가로로 넘기기, 종이 골라 쪽 추가, 어두운 종이, 필기 포함 PDF 내보내기, LaTeX 수식
- AI 펜: 동그라미 친 부분을 Claude가 설명(필요하면 웹 검색), 이어 묻기, 설명 창 크기 조절, 질문 목록(문서 화면 위의 말풍선 단추, AI 펜을 들었을 때 도구 막대의 단추, 설명 창의 목록 단추)

iPadOS 17.5 이상에서 돈다.

## AI 펜

도구 막대의 반짝이 모양이 AI 펜이다. 모르는 부분에 동그라미를 치거나 밑줄을 그으면 그 쪽 전체 그림과 표시한 부분의 확대 그림, 문서 본문 텍스트가 Claude에게 가고, 설명이 옆(가로 화면)이나 아래(세로 화면) 창에 글자가 오는 대로 나온다. 창 아래에서 이어서 물을 수 있다.

- 처음 한 번, 설정(서재 왼쪽 위 톱니바퀴 또는 문서 화면의 ⋯ → 설정)에 본인의 Claude API 키를 넣어야 한다. 키는 <https://console.anthropic.com> 의 API Keys에서 만든다. 사용한 만큼 요금이 나온다.
- 키는 아이패드의 키체인에만 저장되고 api.anthropic.com으로 보내는 요청에만 쓰인다. 키체인이 받아 주지 않는 드문 경우에는 앱 내부 저장소의 파일(파일 앱에서 보이지 않고 백업에서 빠지는 곳)에 둔다.
- 기본 모델은 Opus 5.5다. 가장 정확하지만 질문당 비용도 가장 높다. 설정에서 Sonnet 5.5나 Haiku 5.5로 바꿀 수 있고, 설명 깊이·언어·문서를 얼마나 참고할지도 거기서 고른다.
- 표시는 쪽에 청록색으로 남고 옆에 작은 단추가 붙는다. 단추를 누르거나(손가락 필기가 꺼져 있으면 표시 안쪽을 손가락으로 눌러도 된다) AI 펜으로 표시를 톡 건드리면 저장된 설명이 다시 열린다. 이때는 Claude에게 다시 묻지 않는다.
- 웹 검색: 설정에서 켜 두면(기본값) 요청에 `web_search_20250305` 도구가 함께 간다. 검색할지는 Claude가 정하고, 검색한 답에는 근거가 된 쪽의 번호와 끝에 출처 목록이 붙는다. 한 답에 최대 3번, 검색 1,000회에 10달러가 토큰 요금과 따로 든다. 이어 물을 때는 검색 호출과 결과, 인용이 받은 그대로(봉인된 부분 포함) 되돌아간다. 조직에서 웹 검색을 꺼 둔 키면 검색 없이 답하고 그렇게 알린다.
- 표시를 치우는 방법: 설명 창의 ⋯ → "쪽의 표시만 지우기"(설명은 남는다) 또는 "이 표시와 설명 삭제", 단추를 길게 눌러 나오는 같은 메뉴, 문서 화면 ⋯ → "AI 표시 보이기"를 꺼서 전부 숨기기. 지우개로 표시를 문질러도 표시만 쪽에서 사라진다(실행 취소로 되돌아오고, 지우개 설정에서 끌 수 있다). 지운 표시의 설명은 질문 목록에 남아 있고, 목록에서 그 질문을 길게 누르거나 오른쪽으로 밀면 표시를 다시 보이게 할 수 있다.

## 맥 없이 빌드하기

개발 PC가 Windows라서 빌드는 GitHub Actions의 macOS 러너가 한다.

- `project.yml`: XcodeGen 설정. 빌드 서버가 여기서 Xcode 프로젝트를 만든다(프로젝트 파일은 저장소에 두지 않는다).
- `.github/workflows/build.yml`: `main`에 올릴 때마다 시뮬레이터용으로 빌드해 화면을 찍고, 아이패드용으로 빌드해 서명 없는 IPA를 만든다.
- 결과물은 Actions → 해당 실행 → Artifacts에 있다: `AIPencil-ipa`(설치 파일), `screenshots`(시뮬레이터 화면과 아래의 가짜 서버 기록), 실패하면 `logs`.
- `tools/mock_claude.py`: Claude API를 흉내 내는 가짜 서버. 빌드 서버가 이것을 띄우고 디버그 빌드를 `-apiBase http://127.0.0.1:8787`로 실행해, 키 없이 "표시 → 요청 → 글자가 흘러나옴 → 이어 묻기"를 끝까지 돌려 본다. 앱이 보낸 요청의 요약(`mock.log`)과 함께 간 그림(`mock-dump/`)이 결과물에 들어 있다. 릴리스 빌드(IPA)는 `-apiBase`를 무시한다.
- `tools/tricky.pdf`: 돌아간 쪽과 잘린 쪽이 있는 시험용 PDF. 그런 쪽에서도 Claude에게 가는 그림의 표시 위치가 화면과 같은지 본다.

## 아이패드에 설치하기

IPA에는 서명이 없어서 그대로는 설치되지 않는다. Windows의 Sideloadly가 본인 Apple ID로 서명해 넣어 준다.

1. Artifacts에서 `AIPencil-ipa`를 내려받아 압축을 풀면 `AIPencil.ipa`가 나온다.
2. PC에 Sideloadly와 iTunes(Apple 기기 드라이버)를 설치하고, 아이패드를 USB로 연결해 "이 컴퓨터를 신뢰"를 누른다.
3. Sideloadly에 `AIPencil.ipa`를 끌어다 놓고 Apple ID를 입력한 뒤 Start.
4. 아이패드에서 설정 → 일반 → VPN 및 기기 관리 → 본인 Apple ID → 신뢰.
5. 설정 → 개인정보 보호 및 보안 → 개발자 모드를 켜고 재시동한다(iPadOS 16 이상).

무료 Apple ID로 서명한 앱은 7일 뒤 만료된다. 같은 방법으로 다시 설치하면 되고, 앱 안의 문서와 필기는 남는다. Sideloadly의 자동 갱신을 켜 두면 PC와 같은 Wi-Fi에 있을 때 알아서 갱신한다.

필기는 PDFKit의 쪽 오버레이(iPadOS 16)에 쪽마다 PencilKit 캔버스를 하나씩 얹어 받는다. 캔버스의 좌표는 쪽 왼쪽 위에서 잰 쪽 좌표와 같다(빌드 서버에서 제목 둘레에 고리를 그려 확인했다). PDFKit은 오버레이를 늘려서 확대하므로 그대로 두면 필기의 픽셀도 같이 늘어나 선이 흐려진다. 그래서 캔버스를 확대 배율만큼 크게 만들어 자기 그림을 그만큼 확대해 그리게 한 뒤 쪽 크기로 줄여 놓는다. 좌표는 그대로이고 픽셀만 그만큼 많아진다. 쪽 전체를 덮는 캔버스는 쪽의 3배까지만 만든다(그보다 크면 메모리와 그리는 일이 너무 커진다). 0.7.0까지는 그래서 3배 넘게 확대하면 필기만 거칠어졌다: 화면 맞춤이 2.27배이고 5배까지 확대되는 아이패드에서 캔버스 타일은 점당 6픽셀, 쪽 타일은 10픽셀이었다(0.7.0의 진단 정보로 받은 수치). 0.7.1부터는 그 크기를 넘는 배율에서 캔버스가 쪽 전체가 아니라 보이는 부분과 그 둘레만 덮는다(`canvasWindow`). 캔버스는 스크롤 뷰이므로 그림은 여전히 쪽 전체이고 그 부분으로 스크롤해 둘 뿐이다. 캔버스가 차지하는 크기는 전과 같거나 작고, 세밀함은 PDFKit이 확대되는 데까지(5배) 화면 해상도를 따라간다. PDFKit의 스크롤 뷰를 지켜보다가 보이는 부분이 캔버스 밖으로 나가려 하면 캔버스를 옮기며, 펜이 닿아 있는 동안에는 옮기지 않는다. 3배 이하에서는 0.6.0과 똑같이 쪽 전체를 덮는다. 돌려서 보여 주는 쪽(/Rotate가 있는 쪽)에서는 PDFKit이 오버레이를 돌리기 전 쪽의 틀로 놓고 쪽과 함께 돌린다. 그래서 필기와 표시는 돌리기 전 좌표로 저장되고, Claude에게 보낼 그림을 만들 때만 화면에 보이는 방향으로 돌려 그린다. 펜, 형광펜, 지우개, 올가미는 쪽 위의 도구 막대에서 고른다.

수식은 상단의 Σ 버튼에서 LaTeX로 입력한다. KaTeX로 조판한 미리보기를 그림으로 떠서(글자 모양만 남기고 색은 그릴 때 입힌다) 쪽의 필기 아래에 놓는다. 도구 막대의 "수식 옮기기"를 고르면 필기 캔버스가 비켜서, 수식을 끌어 옮기거나 길게 눌러 수정·복제·삭제할 수 있다.

빈 쪽은 PDF 자체에 끼워 넣고, 그 뒤 쪽들의 필기 파일과 수식·질문의 쪽 번호를 한 쪽씩 뒤로 옮긴다.

AI 펜은 PencilKit의 펜으로 그리게 한 뒤, 획이 끝나면 그 획을 캔버스에서 도로 빼서 표시로 따로 보관한다(필기와 섞이지 않고, 지우개나 올가미에 걸리지 않는다). Claude에는 공식 Swift SDK가 없어 HTTPS로 직접 요청한다. 요청 형식은 안드로이드판과 같다: 지침과 문서 본문(1시간 캐시)을 system에, 쪽 그림 두 장과 질문을 messages에 넣고 스트리밍으로 받는다. 이어 물을 때는 앞선 답의 블록(생각 블록과 서명 포함)을 받은 그대로 되돌려 보낸다.

펜 종류는 만년필(누르는 힘에 따라 굵기가 변함), 펜(조금 변함), 볼펜(굵기 일정), 연필이다. 연필만 PencilKit의 잉크이고 나머지는 앱 자체 펜이다(아래). 굵기는 종이 위의 밀리미터로 정한다(0.8.0): 0.5는 쪽에서 0.5mm, 곧 1.42포인트다. 도구 막대에 굵기 세 칸이 있어 눌러서 바꾸고, 쓰고 있는 칸을 한 번 더 누르면 뜨는 창의 슬라이더가 그 칸의 굵기를 0.05mm씩 바꾼다. 0.7.1까지는 PencilKit의 굵기 값을 그대로 슬라이더에 올려서, 값 1이 선 2포인트였고 2.3 아래에서는 또 다른 기울기라 조금만 움직여도 굵기가 크게 달라졌다. 전에 저장된 굵기는 같은 굵기의 밀리미터 값으로 옮겨진다. 실행 취소는 창의 실행 취소 기록을 쓴다.

애플 펜슬 두 번 탭과 꽉 쥐기는 `UIPencilInteraction`으로 받는다. 무엇을 할지는 앱 설정에서 고르고, "아이패드 설정 따르기"로 두면 시스템의 펜슬 설정을 따른다.

돌려서 보여 주는 쪽에 넣은 수식은 쪽이 돌아간 만큼 반대로 돌려서 화면에서 똑바로 서게 한다.

도구 막대는 도구마다 내용이 다른 오른쪽 칸의 폭을 고정해서, 어떤 도구를 들어도 크기와 자리가 같다.

iOS 27과 선명도: 0.6.0까지 받은 "문서가 낮은 해상도로 보인다", "필기가 낮은 해상도로 보인다"는 보고는 iPadOS 27.2의 실기기에서 나왔고, 빌드 서버의 시뮬레이터(iOS 26)에서는 한 번도 나오지 않았다. iOS 27의 PDFKit에는 쪽 위의 일부 레이어를 1배 해상도로 그려 늘려 보여 주는 결함이 보고돼 있다(주석 레이어 `PDFPageLayerAnnotationEffect`의 `contentsScale`이 1.0, 애플 개발자 포럼 845260·847155, FB24882188). 이 앱에서 무엇이 그 영향을 받는지는 실기기의 수치로만 알 수 있어서, 설정의 진단 정보에 보고 있는 쪽의 레이어마다 크기와 해상도 배율을 적어 넣는다(`describeView`). 쪽 내용은 아래의 "한 번 더 그리기"로 실기기에서 선명해진 것을 확인받았다.

앱 자체 펜(0.7.0에서는 설정으로 켜는 것이었고, 0.8.0부터는 이것이 펜이다): PencilKit은 쓰는 동안의 선을 자기가 그리고, 손떨림을 펴거나 필압 반응의 세기를 바꾸는 값을 받지 않는다. 0.5.0에는 획이 끝난 뒤에 굵기를 고쳐 넣는 "필압" 슬라이더가 있었는데 손을 뗀 뒤에 선이 바뀌어 어색해서 0.6.0에서 뺐다. 펜(연필 제외), 형광펜, AI 펜의 터치는 앱이 직접 받는다(`PenGesture`). 터치마다 선이 펜 쪽으로 일정 비율씩 다가가게 해서 손떨림을 펴고(획 안정화, 가장 높을 때 선이 펜을 약 0.085초 늦게 따라온다), 누르는 힘으로 굵기를 정해(필압 감도) 화면 해상도의 채운 도형으로 바로 보여 준다. 펜을 떼면 그 선을 PencilKit 획(점마다 굵기가 적힌 "monoline" 잉크)으로 캔버스에 넣는다. 그래서 지우개, 올가미, 실행 취소, 내보내기는 전과 같이 통한다. "pen" 잉크는 굵기를 적어 줘도 선 끝을 가늘고 흐리게 만들어 손을 떼는 순간 모양이 바뀌어서 쓰지 않는다. PencilKit은 점에 적힌 크기대로 선을 그리지 않는다: monoline 잉크는 크기 2 이하에서는 아무것도 그리지 않고, 그 위로 1마다 2포인트씩 굵어진다(빌드 서버에서 크기 4·8·12의 직선이 4·12·20포인트로 그려졌다). 그래서 선은 눈에 보일 굵기로 계산하고, 넘길 때만 그 굵기가 나오는 PencilKit 크기로 바꾼다(`InkWidth`). 도형 도구도 같은 환산을 쓴다. 만년필은 필압 감도 그대로, 펜은 그 0.4배, 볼펜은 굵기가 일정하다. 연필만 PencilKit이 그린다. AI 펜의 선은 획이 되지 않고 바로 질문이 된다. 손가락으로 쓸 때는 손가락이 조금 움직이거나 0.15초 머문 뒤에 선으로 치고, 그 전에 둘째 손가락이 닿으면 스크롤·확대에 양보한다.

기본값이 끔인 까닭: 쓰는 동안의 선을 PencilKit은 지연을 줄이는 전용 경로로 그리고, 앱은 보통의 레이어로 그린다. 둘의 지연 차이는 실기기에서만 잴 수 있다. 펜이 손을 늦게 따라오게 되는 일은 없어야 하므로, 직접 켜서 비교해 보고 쓰도록 했다. 끄면 0.6.0과 같은 경로로 쓴다.

필기를 앱이 그리기(0.8.0, `InkPaint`): 펜을 떼면 선이 다시 무뎌진다는 보고의 원인은 캔버스 배율이었다. 캔버스를 확대 배율의 4분의 1 단위로 올림해서, 화면 맞춤 2.219배인 아이패드에서 캔버스는 2.25배로 그려진 뒤 70분의 1만큼 줄여져 화면 픽셀과 어긋났다(쓰는 동안의 선은 앱이 화면 픽셀에 맞춰 그리는 도형이라 선명했다). 0.8.0은 두 가지를 했다. 캔버스 배율을 확대 배율과 정확히 같게 했고, 다 쓴 필기도 앱이 직접 그린다: 쪽의 획을 메인 스레드 밖에서 화면 픽셀 그대로의 그림으로 그려 캔버스 대신 보여 준다. 굵기가 점마다 적힌 평범한 획(자체 펜, 도형, 형광펜이 만드는 획)은 쓰는 동안 보이던 것과 같은 도형으로 그리고, 그 밖의 획(연필, 부분 지우개가 자른 획, 예전 버전의 PencilKit 펜 획)은 PencilKit에게 그 자리만 그리게 해서 같은 그림에 넣는다. 선을 쓰면 그 선은 그림에 들어갈 때까지 쓰던 도형 그대로 떠 있고(손을 0.25초쯤 쉬면 그림에 들어간다), 그림은 바뀐 자리만 다시 그린다. 그래서 펜을 떼는 순간 보이는 것이 바뀌지 않는다. 캔버스는 그대로 밑에 있고 획도 그대로 PencilKit 획이다. 캔버스가 보이는 때는 캔버스에서 일하는 도구(올가미, 부분 지우개, 연필)를 들었을 때, 그림이 아직 없을 때, 확대한 채 스크롤해서 그림이 닿지 않는 곳이 보일 때다. 쪽 전체가 1,300만 화소 안에 들면 쪽 전체를 한 장으로 그리고(큰 아이패드의 화면 맞춤 배율이 950만 화소다), 넘으면 보이는 부분과 그 둘레만 그린다. 화면에서 먼 쪽의 그림은 버린다. 그림의 픽셀은 화면의 픽셀에 맞춘다: PDFKit은 쪽을 확대 배율이 정하는 대로 소수점 위치에 놓아서(빌드 서버의 화면 맞춤에서 첫 쪽이 0.6픽셀 어긋나 있었다) 쪽 모서리에서 시작하는 그림은 그만큼 밀려 보이며 선 가장자리가 반 픽셀씩 번졌다. 그래서 그림을 화면 픽셀이 시작하는 자리부터 그리고(`pixelGrid`), 쪽 그림(`PagePicture`)도 같은 자리에 맞췄다. 0.7.0의 "필기 그림"은 쓰는 동안 캔버스로 돌아가서 펜을 댈 때마다 필기가 바뀌어 보였고, 그래서 0.7.1에서 뺐던 것이다. 이번에는 쓰는 동안에도 그림과 도형이 보이고 캔버스로 돌아가지 않는다.

형광펜(0.8.0): PencilKit의 형광펜은 색을 덧칠해서 한 번만 그어도 글자가 흐려지고 겹치면 가려졌다. 이제 형광펜 획은 반투명한 색의 평범한 획으로 저장하고, 화면에는 형광펜만 모은 그림을 쪽 위에 "곱하기"로 얹는다(종이는 형광펜 색이 되고, 그보다 어두운 글자와 펜은 그대로다). 그림 안에서는 불투명하게 그리므로 같은 자리를 여러 번 그어도 더 진해지지 않는다. 어두운 종이에서는 반대로 밝히는 방식으로 얹는다. 예전 버전에서 그은 형광펜도 같은 그림에 들어간다. 내보낸 PDF에는 아직 반투명한 색으로 들어간다(글자는 보이지만 화면보다 조금 흐리다).

곡선(0.9.0): 펜은 1초에 240번(손가락은 60~120번) 자리를 알려 온다. 보통 속도로 쓰면 화면에서 5~10픽셀마다 한 번이라, 그 자리들을 직선으로 이으면 곡선마다 모가 났다. 이제 알려 온 자리는 선의 매듭이고, 매듭 사이는 매듭들을 부드럽게 지나는 곡선(Catmull-Rom)을 1.5픽셀보다 촘촘한 점으로 풀어서 잇는다(`PenLine`). 가장 새 매듭까지의 구간은 다음 매듭이 와야 곡선이 정해지므로 그때까지는 임시로 그려 두었다가 다시 계산한다. 넘겨 주는 획의 점도 이 촘촘한 점이라 펜을 뗀 뒤에도 같은 모양이다. 또 하나는 선 둘레의 원이다. 쓰는 중인 선은 점마다 원을 놓고 그 사이를 띠로 이은 도형인데, 그 도형을 보여 주는 층(CAShapeLayer)이 원을 직선 몇 개로 바꿀 때 화면에 확대된 크기가 아니라 쪽의 1포인트 크기를 기준으로 삼아서, 곡선의 바깥쪽(원이 만드는 부분)이 각져 보였다. 원을 화면 배율에 맞는 수의 변을 가진 다각형으로 직접 만들어 넣는다(`InkPaint.shape`). 빌드 서버에서는 한 바퀴에 8·12·20번만 자리를 알려 준 동그라미가 둥글게 나오는 것을 확인했다. 아이패드에서 애플 펜슬로 쓴 선의 모습은 확인하지 못했다.

쓰는 중인 선(0.10.0, `WetInk`): 0.9.0까지 쓰는 중인 선과 아직 그림에 들어가지 않은 선은 도형 층(CAShapeLayer)으로 보여 줬다. 시스템이 그 층을 그리는 방식은 그림을 그리는 방식과 달라서, 쓰는 동안에는 곡선이 덜 매끄럽고 많이 확대하면 거칠었으며 펜을 뗀 뒤에야 깔끔해졌다. 이제 그 선들도 그림과 같은 코드로, 화면 픽셀에 맞춘 작은 타일(384픽셀)에 그린다. 선이 자라면 자란 부분이 걸친 타일의 그 부분만 다시 그린다. 그림이 그 선을 갖게 되면 타일에서 내리는데, 같은 모양을 같은 픽셀에 그린 것이라 화면에서는 바뀌는 것이 없다. 방금 쓴 선을 지우거나 실행 취소하면 그림을 기다리지 않고 타일에서 바로 내린다(0.9.0에서는 그림이 따라올 때까지 남아 있어서 지워지지 않은 것처럼 보였다). 필기를 처음부터 한 가지 방식으로 그리는 것이 다른 필기 앱들의 방식이고, 이 변경으로 쓰는 중과 쓴 뒤의 그리기가 하나가 됐다. 다 쓴 필기를 큰 그림 한 장으로 두는 것은 그대로다(쪽 전체가 한 장에 들어가는 배율에서는 스크롤해도 다시 그릴 일이 없다). 많이 확대했을 때는 보이는 부분만 그림으로 그리므로, 스크롤해서 그 밖으로 나가면 곧바로 새 그림을 청하고(전에는 다음 점검 때까지 기다렸다) 그동안 보이는 캔버스도 확대 배율 그대로 그리게 했다(전에는 8배까지).

도구 설정 창(0.10.0): 손에 든 도구를 한 번 더 누르면 뜨는 설정은 팝오버(내용 크기에 맞춰 스스로 크기를 정하는 별도 창)였다. 아이패드의 충돌은 "문서를 열고 펜을 눌렀을 때" 났고 스택은 그 창이 배치되는 자리였다. 이제 도구 막대 아래에 놓이는 보통 카드이고, 다른 곳을 누르면 닫힌다. 안의 색 격자도 필요할 때 칸을 만드는 격자에서 평범한 줄로 바꿨다. 아이패드에서 충돌이 없어졌는지는 확인되지 않았다.

쪽 고르기와 합치기(0.9.0, `PDFCopy`): 고른 쪽의 객체를 원래 파일에 적힌 그대로(글꼴, 그림, 압축된 스트림까지) 새 파일로 옮겨 적는다. 다른 쪽은 새 파일에 들어가지 않고, 옮긴 쪽의 글자는 원본과 같다. 쪽에서 다른 쪽을 가리키는 링크는 그 쪽이 함께 옮겨질 때만 남는다. 합치기는 문서마다 내보내기와 같은 사본(필기를 그려 넣은 것)을 만든 뒤 그 쪽들을 한 파일로 옮긴다. 암호화된 PDF는 이렇게 읽을 수 없어서 PDFKit이 쪽을 새로 써서 만든다(이 경우 일부 글꼴의 글자 정보가 깨질 수 있다).

스레드: PDFKit의 문서와 쪽 객체는 여러 스레드에서 함께 쓰라고 만든 것이 아니다. 0.6.0은 화면에 떠 있는 문서의 쪽을 그리기 큐와 쪽 이동 창의 그림 작업에서도 썼다. 0.7.0부터 그리기 큐와 쪽 이동 창은 같은 파일을 따로 연 자기 사본만 쓴다(`PictureSource`, `ThumbnailSource`).

메모리: 메모리 부족 경고를 받으면 안 보이는 쪽의 그림을 버리고, 그 문서를 닫을 때까지 그림의 화소 한도를 절반으로, 캔버스의 배율 상한을 3배에서 1.5배로 낮춘다.

진단(설정 → 진단): 빌드 서버에서는 실기기에서 생기는 일을 볼 수 없어서, 앱이 화면에 떠 있다가 끝난 실행의 수, 메모리 부족 경고의 수, 시스템(MetricKit)이 알려 주는 충돌·멈춤·종료 사유, 그리고 마지막으로 보던 쪽의 레이어별 해상도를 아이패드 안에 적어 둔다. "진단 정보 복사"로 글로 꺼낼 수 있고, 앱이 어디로 보내지는 않는다.

쪽을 한 번 더 그리기: 쪽이 화면에 가까이 오면 앱이 그 쪽을 화면 해상도 그대로 메인 스레드 밖에서 그려 PDFKit의 그림 위에 덮는다(`PagePicture`, 쪽 오버레이의 맨 아래 층). 한 쪽이 900만 화소를 넘게 되는 배율에서는 보이는 부분과 그 둘레만 그리고, 스크롤해서 그 밖으로 나가면 다시 그린다. 그림이 준비되기 전과 그림이 닿지 않는 곳에는 PDFKit의 그림이 보인다. 화면에서 한 화면 반 넘게 벗어난 쪽의 그림과 메모리가 모자랄 때 안 보이는 쪽의 그림은 버린다. 문서 안 검색에서 찾은 낱말의 노란 표시는 PDFKit의 것이 이 그림에 가려지므로 오버레이에 직접 그린다. 0.8.0부터는 늘 켜져 있고 설정이 없다.

이 층은 "실기기에서 문서가 다른 필기 앱보다 낮은 해상도로 보인다"는 보고 때문에 넣었는데, 빌드 서버의 시뮬레이터에서는 그 현상이 나오지 않았다. 글자 PDF(맞춤 배율, 2.5배, PDFKit이 허용하는 최대 배율), 화면보다 훨씬 큰 쪽, 쪽 전체가 스캔 그림인 문서(밝은 종이와 어두운 종이)를 이 층을 켠 화면과 끈 화면으로 찍어 비교하면 글자 PDF는 회색 단계 하나 안쪽으로 같고, 스캔본은 그림을 줄이고 늘리는 방식이 조금 다를 뿐 눈으로 구별되지 않는다. 그러니 이 층이 실기기에서 무엇을 바꾸는지는 아이패드에서 켜고 끄며 봐야 안다. 쪽이 미리 그려져 있다는 점은 시뮬레이터의 정지 화면으로는 잴 수 없다.

지우개: 획 지우개는 앱의 것이고(0.8.0) 부분 지우개는 PencilKit의 것이다. 둘 다 크기가 있고(화면 포인트 6~60, 도구 막대에 세 가지), 쪽에 보이는 원이 지우는 범위다: 획 지우개는 원에 닿은 획을 통째로 지우고, 부분 지우개는 원이 지나간 자리만 지운다. 획 지우개는 지우개가 내려올 때 쪽의 획과 각 획이 차지하는 자리를 한 번 적어 두고, 움직이는 동안에는 그 자리에 들어간 획만 살핀다. "형광펜만 지우기"는 같은 지우개가 형광펜 획만 고르는 것이다. 한 번 문지른 것이 실행 취소 한 단계다. AI 펜 표시는 아무 터치도 가로채지 않는 제스처 인식기(`TouchWatcher`)가 지우개의 자리를 따라가며 지난 곳을 찾는다. 원은 지우는 동안, 그리고 애플 펜슬을 화면 위에 띄우고 있는 동안 보인다. PencilKit의 부분 지우개는 굵기 값만큼의 화면 포인트를 지운다(빌드 서버에서 화면 맞춤 배율로 잰 값: 굵기 40은 40포인트, 16은 16포인트; 확대한 상태에서는 재지 못했다).

확대와 이동(0.8.0): 축소는 한 쪽이 통째로 보이는 데서 조금 더까지만 된다. 확대는 화면 너비 맞춤의 6배까지다(PDFKit의 기본 한도인 쪽 크기의 5배는 큰 아이패드에서 화면 맞춤의 2.2배밖에 안 됐다). PDFKit의 스크롤 뷰는 드래그를 시작한 방향(가로 또는 세로)으로만 움직이게 잠겨 있어서 그 잠금을 풀었다: 확대한 쪽이 손가락이 가는 대로 비스듬히도 움직인다.

충돌과 멈춤(0.7.1의 진단 기록): 받은 기록 세 건은 모두 메인 스레드가 화면을 그리는 SwiftUI 내부에서 멈추거나 죽은 것이었다. 진단 코드가 시스템의 충돌 보고를 받는 스레드에서 설정 저장소(UserDefaults)에 횟수를 쓰고 있었고, 화면들이 그 저장소를 지켜보고 있어서 두 스레드가 화면 상태를 동시에 건드릴 수 있었다(세 건 중 두 건이 보고를 받은 실행에서 몇 분 안에 일어났다). 0.8.0은 저장소를 메인 스레드에서만 쓰고, 슬라이더를 끄는 동안 값이 바뀔 때마다 저장하던 것을 멈춘 뒤 한 번 저장하게 했다. 첫 번째 멈춤은 이것으로 설명되지 않아 원인이 확인된 것은 아니다. 그래서 진단을 보강했다: 메인 스레드가 3초 넘게 대답하지 않으면 그때 앱이 하던 일(마지막 몇 단계)을 기록하고, 충돌 보고의 호출 스택을 끝까지(앱 자신의 코드가 나오는 데까지) 적으며, 빌드마다 기호 파일(dSYM)을 남겨 그 위치를 이름으로 찾을 수 있게 했다. AI 펜을 든 동안 실행 취소 기록을 꺼 두던 코드도 없앴다(AI 펜이 캔버스에 쓰지 않게 되어 필요가 없어졌고, 껐다 켜는 짝이 어긋나면 예외가 나는 코드였다).

충돌(0.8.0의 진단 기록): 0.8.0에서도 같은 자리의 충돌이 세 번 이어졌다(설치 직후 1분 안에 세 번 실행, 세 번 모두 SwiftUI의 화면 갱신 안에서 SIGSEGV; 그 뒤로는 잘 돌았다). 호출 스택을 끝까지 적게 한 덕에 메인 스레드라는 것, 화면 배치 → SwiftUI 갱신 → AttributeGraph 순서라는 것은 알았지만 시스템 코드의 이름은 알 수 없고 앱 자신의 코드는 맨 바깥(main)뿐이라 원인은 여전히 확정하지 못했다. 0.9.0은 세 가지를 바꿨다. 실행 중의 단계를 그때그때 파일에 적어 두고 다음 실행이 읽는다(충돌한 실행이 무엇을 하다가 몇 초 만에 끝났는지가 진단 정보에 남는다). 서재의 격자를 화면에 들어올 때 카드를 만드는 시스템 격자(LazyVGrid)에서 모든 카드를 한 번에 놓는 자체 배치(`ShelfGrid`)로 바꿨다(스택의 모양이 목록의 자식을 넣고 빼는 자리와 닮았고, 실행 직후 화면 크기가 정해지는 동안 일어난 것으로 보여서다). 문서를 열 때 "최근에 연 순서"를 바로 바꾸지 않고 화면이 자리 잡은 뒤에 바꾼다(문서를 여는 전환 도중에 서재 목록의 순서가 바뀌지 않게). 이 셋은 추정에 따른 방어이고, 원인을 고쳤다고 확인된 것은 아니다.

쓰고 나면 이전 도구로: 지우개·형광펜·도형마다 설정에 스위치가 있다. 켜 두면 한 번 쓰고 펜을 떼는 순간 그 전에 들고 있던 도구로 돌아간다.

저장과 속도: 필기는 바뀔 때마다 바로 쓰지 않고 0.8초 뒤에 메인 스레드 밖에서 쓴다(앱을 떠날 때, 문서를 닫을 때, 내보내기와 쪽 추가 전에는 기다리지 않고 바로 쓴다). PDF 가져오기의 파일 복사, 서재의 표지 그리기, 쪽 이동 창의 쪽 그림도 메인 스레드 밖에서 하고, 표지는 한 번 그려 문서 옆에 `cover.jpg`로 둔다.

도형은 끄는 동안 미리보기 선으로 보이다가 손을 떼면 굵기가 일정한 PencilKit 획이 된다. 그래서 지우개·올가미·실행 취소가 그대로 통한다.

어두운 종이는 쪽을 그릴 때 흰 바탕에 쪽을 그린 뒤 밝기를 뒤집고(차이 혼합), 쪽을 한 번 더 그려 색상만 되돌린다(색상 혼합). 필기는 PencilKit이 어두운 화면용 색으로 보여 준다. 내보내기와 Claude에게 가는 그림은 따로 연 문서로 만들어 늘 원래 색이다.

가져온 PDF는 다시 쓰지 않는다. PDFKit으로 문서를 저장하면(`PDFDocument.write`) 모든 쪽을 새로 그려 넣은 파일이 만들어지는데, 그 파일에서는 한글 글꼴처럼 일부만 넣은 글꼴의 글자 정보가 깨져서 글자를 뽑으면 엉뚱한 글자가 나온다. 0.4.0까지는 "쪽 추가"가 이 방식이어서, 쪽을 추가한 문서는 Claude에게 가는 본문과 문서 안 검색이 깨졌다. 지금은 추가한 쪽을 PDF 옆의 `pages.json`에 적어 두고 문서를 열 때마다 끼워 넣는다(`DocFile.open`). 0.4.0 이하에서 쪽을 추가했던 문서는 파일이 이미 바뀌어 있으니, 글자가 필요하면 원본을 다시 가져와야 한다.

노트 종이는 줄이 그려진 실제 PDF 쪽이다. 무늬는 한 번 계산해서 화면용 쪽에도, 내보내기에도 같은 것을 쓴다.

내보내기는 원본 파일을 그대로 두고 그 뒤에 바뀐 부분만 덧붙인다(PDF의 증분 갱신, `PDFAppend`). 필기·수식·표시는 쪽마다 그림 한 장(쪽의 3배 해상도, 쓴 곳만 잘라서)으로 쪽 내용 끝에 얹히고, 추가한 쪽은 새 쪽으로 들어간다. 원본의 바이트가 그대로라 글자 선택·검색·복사가 원본과 같다. 암호화됐거나 구조가 어긋난 파일은 덧붙일 수 없어서 PDFKit으로 새로 써서 내보내며, 이때는 보이는 모습은 같아도 글자 정보가 달라질 수 있다. 암호 없이 열리지만 인쇄·복사 등이 제한된 PDF는 PDFKit이 그대로 쓰면 어떤 암호로도 열리지 않는 파일이 나오므로, 원본과 같은 권한으로 다시 잠가서 쓴다(여는 데 암호는 필요 없고 제한은 유지). 써 놓은 파일이 열리지 않으면 내보내기를 실패로 처리한다. 덧붙이는 방식은 먼저 파이썬 기준 구현으로 실제 PDF 370여 개(표 형식·스트림 형식 교차 참조, 객체 스트림, 선형화, 여러 번 갱신된 파일 포함)에 돌려 봤고, 암호가 걸린 2개와 손상된 1개를 뺀 전부가 통과했다. 앱의 Swift 코드는 그 구현을 그대로 옮긴 것이고, 빌드 서버에서 네 가지 문서(쪽을 추가한 샘플, 돌려지고 잘린 쪽이 있는 문서, 객체 스트림을 쓰는 문서, 쪽을 추가한 줄 노트)를 내보내 쪽 그림과 글자를 확인한다.

## 직접 확인하지 못한 것

0.8.0에서 빌드 서버로 확인한 것: 손가락으로 쓴 선이 쓴 직후(앱이 도형으로 보여 주는 동안)와 2초 뒤(필기 그림에 들어간 뒤)에 같은 픽셀로 그려지는지(천천히 쓴 두 선은 가장자리 픽셀 값까지 같았고, 빠르게 쓴 선은 0.4픽셀쯤 옮겨질 뿐 가장자리 폭은 같았다; 화면 픽셀에 맞추기 전에는 선마다 양쪽으로 반 픽셀씩 번졌다), 쪽 글자의 가장자리(글자 블록에서 중간 밝기 픽셀의 비율이 PDFKit만일 때 0.92, 맞추기 전 0.87, 맞춘 뒤 0.54), 글자 위에 그은 형광펜 아래에서 글자가 그대로 검은지와 겹친 자리가 한 번 그은 자리와 같은 색인지, 크기 48과 8의 획 지우개와 실행 취소, 확대한 채 비스듬히 끌었을 때 가로·세로로 함께 움직이는지, 축소와 확대의 한계, A5 가로와 A3 노트, 연필(PencilKit)로 쓰기. 확인하지 못한 것: 애플 펜슬로 쓸 때의 지연과 필압, 아이패드(iPadOS 27)에서의 선명도와 메모리, 충돌이 실제로 없어졌는지(원인으로 지목한 것은 시뮬레이터에서 재현되지 않았다), 파일 앱 공유 시트에 앱이 보이는지, 필기가 아주 많은 쪽에서 그림을 처음 그리는 시간(시뮬레이터에서는 PencilKit이 그려야 하는 예전 획이 있는 쪽이 0.3~1초 걸렸다. 그동안은 캔버스가 보인다).

빌드 서버의 시뮬레이터에서 가짜 서버로 확인한 것까지가 검증 범위다. 0.6.0부터는 시뮬레이터에서 손가락 터치를 실제로 넣는 테스트(`AIPencilUITests`, `uitests.yml`)가 있어서, 손가락 필기로 AI 펜 표시 만들기, 지우개로 표시 지우기와 실행 취소, 펜과 형광펜 긋기, 형광펜만 지우기, 지운 뒤 이전 도구로 돌아가기, 도형 끌어 그리기를 빌드 때마다 해 본다. 애플 펜슬은 시뮬레이터에 없어서 펜슬로 하는 같은 동작은 확인하지 못했다. 0.7.0의 앱 자체 펜은 손가락 터치로 세 줄을 잇달아 쓰고, 실행 취소하고, PencilKit 펜으로 쓴 직후와 손을 멈춘 뒤의 화면을 찍는 것까지 이 테스트에 들어 있다. 0.7.1부터는 최대 배율로 확대한 채로 쓰기(PencilKit 펜과 앱 자체 펜), 손가락으로 스크롤하기, 지우기도 한다: 선은 손가락이 지나간 자리에 그려지고, 캔버스 타일은 점당 10픽셀(5배 × 2)로 만들어진다. 앱 자체 펜이 손을 따라오는 지연, 필압 감도와 획 안정화의 실제 느낌, 확대한 채 빠르게 스크롤할 때 캔버스가 따라오는 모습, 애플 펜슬을 띄웠을 때 지우개 원이 보이는지는 아이패드에서만 알 수 있다. 실제 Claude API 호출(웹 검색 포함), 실제 애플 펜슬로 그은 획과 필압, 펜슬 두 번 탭·꽉 쥐기, 손가락으로 표시를 눌러 여는 동작, 실기기의 키체인 저장은 아이패드에서 직접 해 봐야 안다.

내보내기는 시뮬레이터에서 만든 파일을 맥의 PDFKit, pypdf, pdf.js 세 가지로 열어 쪽 수·글자·그림을 확인했다. 내보낸 뒤 뜨는 공유 창, 수백 쪽짜리 문서를 내보낼 때 걸리는 시간과 메모리, 다른 앱(굿노트, 어도비 등)에서 열었을 때의 모습은 확인하지 못했다. 암호화된 PDF의 내보내기는 열리고 모습도 맞지만 글자 정보는 깨진다(위에 적은 PDFKit의 한계).
